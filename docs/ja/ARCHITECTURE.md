# アーキテクチャ

背景と根拠は [DESIGN.md](DESIGN.md) にあります。本書は現時点の構成と方針の記録であり、確定仕様ではありません。

## 構成

crate は一つ（lib + bin）で、依存は 1 つ（`-P` のための `pcre2-sys`）です。依存境界が固まるまで workspace 分割はしません。

| モジュール                | 担当すること                                                                                                                                         | 担当しないこと                                         |
|----------------------|------------------------------------------------------------------------------------------------------------------------------------------------|-------------------------------------------------|
| `syntax`             | トークン化、AST、ソース位置、構文診断（`parser`）                                                                                                                 | 実行、ファイル書き込み                                     |
| `regex`              | 正規表現エンジン：BRE/ERE の方言（GNU grep の構文も）、左端最長一致、キャプチャ。`Regex::compile_pcre` が、PCRE2 のパターンを同じインターフェースの裏に包みます                                         | sed の構文、置換                                      |
| `pcre`               | `pcre2-sys` を通した PCRE2 ライブラリ：コンパイル、マッチ、グループのオフセット（`sed -P`、`grep -P`）                                                                          | マッチが sed や grep にとって何を意味するか                     |
| `locale`             | 実行のロケール（C ライブラリが決めます）と、マッチャーと `\U \L` が呼ぶ少数のライブラリ関数（`towupper`、`iswalnum`、ブラケット式のための `regcomp`/`regexec`）                                      | `C.utf8` の表（`regex::classes_table`）             |
| `runtime`            | サイクル、pattern/hold space、コマンド評価、`s` と `y`、`l`                                                                                                   | CLI 引数の解釈                                       |
| `io`                 | レコードの読み込み、出力ストリーム、`w` ファイル、インプレース編集、標準入力                                                                                                       | スクリプト構文                                         |
| `debug`              | `--debug` のプログラムの正規形と実行トレース                                                                                                                    | スクリプトの実行                                        |
| `cli`                | オプション解析、モード決定、終了状態                                                                                                                             | 変換ロジックの別実装                                      |
| `analysis`           | スクリプトがレコード内で完結する（チャンクごとに独立して実行できる）かを静的に判定する                                                                                                    | スクリプトの実行                                        |
| `parallel`, `stream` | 順序つきチャンクストリーム、ワーカー、出力の順序つきマージ                                                                                                                  | スクリプトの意味                                        |
| `search`             | バイト・部分文字列検索（SSE2/AVX2、スカラー実装へのフォールバック付き）。ASCII 文字の大文字小文字を区別しない検索もある                                                                            | 正規表現                                            |
| `api`, `edit`        | 公開する Rust のインターフェース。`Script`、`Run`、`Error`、および `Address` と `Pattern` を使うビルダー `Edit`                                                            | コマンドの意味（それはパーサーと VM が持つ）                        |
| `grep`               | grep モード。GNU grep のオプション（`options`）、パターンと「一致」とは何か（`matcher`）、入力の検索と文脈つきの行の出力（`search`）、名前・`-r`・`--include`（`glob`）、色（`color`）、`-P`（`pcre` を通す） | 正規表現の構文（`regex` エンジンは、求められたときに GNU grep の構文を読む） |

## 正規表現エンジン

検索は最大3段階を通ります。後の段階ほど高価で、どの段階も NFA シミュレーションと完全に同じ結果を返します。

1. **リテラル先読み**（`regex::literal`）。リテラルだけのパターンは部分文字列検索で答えます。あるリテラルを必須とするパターン（単純なグループにまたがってもよい）は、それを含まない入力をオートマトンを動かす前に弾きます。
2. **遅延 DFA**（`regex::dfa`）は、パターンに後方参照がなく、対象のテキストに区切りの文字や改行のバイトがないときに使います。UTF-8 ロケールでは、文字を UTF-8 のバイト列に展開して DFA をバイト上で動かします。大文字小文字の畳み込みや単語アサーションのあるパターンは、ASCII のテキストに限ります。
   - 前向きで先頭固定でない DFA が最も早いマッチの終わりを見つけ、逆向きの DFA（パターンを鏡像にして作る）が、そこで終わるマッチの最も左の開始位置を見つけます。それより前の開始位置（マッチはもっと後で終わる必要がある）は、作業量の予算の範囲で、前向きで先頭固定の DFA で試します。最も長い終わりは、前向きで先頭固定の DFA が与えます。
   - 状態は必要になったときに作ります（最大 2000。それを超えると探索は別の方法に切り替わります）。
   - 最も早い終わりを先に探すので、1 本の長い行での繰り返しの探索も線形のままです。
3. **NFA シミュレーションとバックトラック**（`regex::exec`）。基準となる実装です。後方参照、非 ASCII 入力、DFA が引き受けないものすべてを扱い、DFA が見つけた範囲に対して部分マッチを割り当てます。

DFA 経路は、ランダムなパターンと入力でシミュレーションと突き合わせ（`regex::tests`）、有効にした状態で fixture と実行 fuzz テストも通しています。

## ロケール

`locale::from_env` は、最初に一度だけ `setlocale(LC_ALL, "")` を呼び、`LC_CTYPE` の文字集合と、`LC_CTYPE`・`LC_COLLATE` の名前を読み戻します。結果は 5 つの `regex::Locale` のどれかで、文字を読むところはすべて、値を比べずに `Locale::is_chars`（テキストを文字として読むか）、`is_utf8`、`is_lib`（ライブラリが答えるか）で尋ねます。

| `Locale`   | 条件                                                                   | 文字とは何か、集合に何が入るか                                                                                         |
|------------|----------------------------------------------------------------------|---------------------------------------------------------------------------------------------------------|
| `C`        | バイト単位：`C`、`POSIX`、インストールされていない名前、UTF-8 以外の文字集合                       | 1 バイト。クラスは ASCII のみ                                                                                     |
| `Utf8`     | `LC_CTYPE` が `C.UTF-8` で、`LC_COLLATE` が `C`、`POSIX`、`C.UTF-8` のどれか   | UTF-8 の 1 文字。`C.utf8` の表を組み込み済み（`classes_table`、`tools/gen-classes.py` で生成）。範囲はコードポイント順。マッチ中にライブラリを呼ばない |
| `Libc`     | それ以外の UTF-8 ロケール                                                     | UTF-8 の 1 文字。以下の問い合わせは C ライブラリに任せる                                                                      |
| `Mb`       | UTF-8 以外のマルチバイト文字集合（EUC-JP、Shift_JIS、GBK、GB18030、Big5、EUC-KR、EUC-TW） | `mbrtowc` で読む 1 文字。以下の問い合わせは C ライブラリに任せる                                                                |
| `Sb`       | ASCII 以外の単一バイト文字集合（ISO-8859-x、KOI8-R、Windows-125x）                   | 1 バイト。括弧式ごとにバイト集合を持ち、256 バイトを C ライブラリに尋ねて埋める                                                            |

`Libc` では、答えがロケールに依存するとき、パーサーは `lib` を持つ `CharSet` を作り、`CharSet::matches_char` がライブラリに尋ねます。

- 範囲・クラス・等価クラス・照合記号を含むか、`I` の下で読まれるブラケット式は、全体を `regcomp` でコンパイルし（エラーコードは GNU sed のメッセージ `Invalid range end`、`Invalid collation character` などになります）、1 文字ずつ `regexec` で試します。
  - 答えは覚えておくので（ASCII は 2 つのビットマスク、それ以外は表）、テキストごとに、異なる文字 1 つにつきライブラリを 1 回呼ぶだけです。
  - GNU sed と同じことをするので、範囲は `LC_COLLATE` の照合順序に、クラスと大文字小文字は `LC_CTYPE` に従い、自前でモデル化するものはありません。
- 単一の文字と ASCII 数字の範囲だけを持つブラケット式があるパターンは、その範囲をコードポイントとして読む形でもう一度コンパイルします（GNU sed の最初のマッチャーがそうします）。この読み方でマッチしないレコードにはマッチせず（`Regex::filter`）、通ったレコードの中のマッチはライブラリのものです（`echo 3٣ | sed 's/[0-9]/N/g'` は `NN`、`echo ٣ | sed 's/[0-9]/N/'` は `٣` を出力します）。
- `I` の下では、リテラルの文字や単一の文字だけのブラケット式は、パターンがその文字自体を書かない限り U+1C80..U+1C88 を取りません（GNU sed の最初のマッチャーについて観察した規則です）。
- `\w`、`\W`、`\s`、`\S` はライブラリにとって `[_[:alnum:]]` と `[[:space:]]` です。単語アサーションは `iswalnum` を使います。
- `I` の下のリテラルの文字は、`REG_ICASE` を付けた `regcomp` でコンパイルし、同じように尋ねます（`tr_TR.UTF-8` では `i` は `İ` と、`I` は `ı` と組になります）。`I` の下の後方参照と `\U \L \u \l` は `towupper`/`towlower` を使います。

`lib` を持つ集合は DFA には不透明です（`expand_utf8` は断ります）。そのため、そのようなパターンは ASCII のヘイスタックでは DFA、それ以外では NFA シミュレーションで動きます。既定の経路は影響を受けません。

**ほかの文字集合。** `regcomp` と `iswalnum` は `wchar_t` で動き、glibc では文字集合によらず `wchar_t` が Unicode なので、上の問い合わせは `Mb` でも `Libc` と同じです。違うのは文字の読み書きだけです。

- 符号化を知っているのは `locale::mb_decode`（`mbrtowc`）と `locale::mb_encode`（`wcrtomb`）だけです。
  - `Searcher::dec` とパーサの `dec` が（`Mb` では）`decode_utf8` に代わり、`LibSet` は文字が書かれているバイト列についてライブラリに尋ね（`contains_seq`。EUC-TW の文字には 2 通りの書き方があり、ライブラリは渡された書き方に答えます）、`\U \L` はワイド文字を経由して変換して書き戻します。
  - `mbrtowc` が拒む、または受け付けてもライブラリ自身のマッチャが `.` に取らないバイト（GBK の 0x80。起動時に調べる）は、UTF-8 と同じく不正バイトです。
- マルチバイトのマッチは文字境界からしか始まらず（`Program::char_starts` は常に有効）、どの歩みも文字全体を消費するので、文字の 2 バイト目だけが単独でマッチすることはありません。
  - `Searcher::dec_before` は、位置の直前の文字を、わかっている境界から行を前向きに読んで見つけます（最寄りの、それ自体が文字である ASCII バイト、または同じ行についての以前の問い合わせで見つかって `BoundaryCache` に覚えた境界。そのため長い行でも線形のままです）。EUC-JP でも 2 バイト目は 1 バイト目としても有効なので、どの文字集合でも後ろ向きの復号はできません。
  - `Mb` では、空マッチのあと `s` のループは 1 バイトではなく 1 文字進みます。
- パターンには、文字全体でない 0x80 以上のバイト（`s/\xa4./X/`。2 バイト文字の先頭バイト）を書けます。また `--glibc-compat` では、括弧式が文字の先頭バイトだけを取ることがあります。
  - そのときマッチは文字の途中で終わります。
  - `Regex::tails` はそうなりうることを表します。`Searcher::dec` は、別の文字の内側の位置では、その文字の残りのバイトだけから文字を読み（glibc は行全体を先頭から復号するので同じです）、文字の内側から始まる検索は次の文字から続けます。
- `locale::ascii_bytes_are_characters`（起動時に `mbrtowc` で測る。0〜127 のバイトが ASCII で、ASCII バイトを含むマルチバイト文字がない）は、DFA とリテラル検索が ASCII バイトを見てよいかを表します。
  - EUC-JP と EUC-KR は満たし、Shift_JIS（0x5c、0x7e）、GBK、Big5（2 バイト目が 0x40〜0x7e）は満たさないので、後者では DFA を使わず、`required` のリテラル（ASCII バイトが ASCII である限り正しい必要条件）だけを使います。
  - `Mb` で `expand_utf8` は使いません。
- `Sb` にデコーダはありません。バイトが文字です。括弧式は `regcomp` で丸ごとコンパイルし、バイト集合は 1 バイトずつ尋ねて埋めます。DFA とリテラル検索はそのバイト集合の上で `C` ロケールと同じように動き、0x80〜0xff の単語構成文字は起動時に埋める表から引きます（`locale::word_byte_high`）。
- GNU sed と同じく、スクリプトは文字単位で読みます（`Parser::multibyte_tail`、`normalize_escapes` の `locale::script_char_len`）。そのため、2 バイト目が `\`、`[`、`]`、区切り文字であっても文字の一部のままです。置換文は、これも GNU sed と同じく、バイト単位で読みます。

## 方針

- 公開する Rust API は小さく、`Script`（`Dialect` で基本・拡張・Perl 風のパターンを選ぶ）、`Edit`（`Address` と `Pattern` を伴う）、`Run`、`Outcome`、`Error` だけです（`src/api.rs`、`src/edit.rs`）。ほかのモジュールはすべて `#[doc(hidden)]` で、コマンドとテストが使うもので、自由に変えられます。
  - `Edit` は sed のテキストを書き、コマンドラインと同じパーサーがそれを読むので、パーサーも VM も 1 つだけで、メソッドで作ったスクリプトは手で書いたスクリプトと同じものです。テキストは `Script` を作るときに検査され、`Run` は自分の設定（ロケール、`-z`、サンドボックス、`--glibc-compat`）でもう一度パースします。
  - CLI は同じモジュールの上の薄い層です（パースして、実行する）。
  - レコード単位で完結するスクリプトは、順序つきのチャンク列の上で並列に動きます（コマンドラインの大きな通常ファイル、またはメモリ上のリーダーやバイト列に対する `Run::jobs`）。それ以外は逐次の VM で動きます。
- 未対応構文はコンパイル時エラーとし、黙って別の意味に解釈しません。
- 入力はバイト列として保持します。レコード末尾の区切りは本文と区別して扱います。

## 由来とライセンス

- GNU sed と GNU grep のソースコードはコピーせず、読むこともしません。挙動は、ツールを動かして調べました（D12）。ソースを参照する必要があったときは、別の読み手が、観察できる規則だけを渡しました。`reference/` 以下の clone は追跡しません。PCRE2 は BSD ライセンスなので、ソースを読んで移植してかまいません（D14）。
- テストの期待値は GNU sed をコマンドとして実行して生成します（リポジトリの `tests/README.md` を参照）。
- プロジェクトは `MIT OR Apache-2.0` でライセンスされています。このライセンスと衝突するため、GPL のコードに由来するものは追加してはいけません。
