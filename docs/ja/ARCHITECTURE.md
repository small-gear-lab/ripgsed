# アーキテクチャ

背景と根拠は [DESIGN.md](DESIGN.md) にあります。本書は現時点の構成と方針の記録であり、確定仕様ではありません。

## 構成

crate は一つ（lib + bin）。依存境界が固まるまで workspace 分割はしません。

| モジュール                | 担当すること                                                                                                    | 担当しないこと                             |
|----------------------|-----------------------------------------------------------------------------------------------------------|-------------------------------------|
| `syntax`             | トークン化、AST、ソース位置、構文診断（`parser`）                                                                            | 実行、ファイル書き込み                         |
| `regex`              | 正規表現エンジン：BRE/ERE の方言、左端最長一致、キャプチャ                                                                         | sed の構文、置換                          |
| `locale`             | 実行のロケール（C ライブラリが決めます）と、マッチャーと `\U \L` が呼ぶ少数のライブラリ関数（`towupper`、`iswalnum`、ブラケット式のための `regcomp`/`regexec`） | `C.utf8` の表（`regex::classes_table`） |
| `runtime`            | サイクル、pattern/hold space、コマンド評価、`s` と `y`、`l`                                                              | CLI 引数の解釈                           |
| `io`                 | レコードの読み込み、出力ストリーム、`w` ファイル、インプレース編集、標準入力                                                                  | スクリプト構文                             |
| `debug`              | `--debug` のプログラムの正規形と実行トレース                                                                               | スクリプトの実行                            |
| `cli`                | オプション解析、モード決定、終了状態                                                                                        | 変換ロジックの別実装                          |
| `analysis`           | スクリプトがレコード内で完結する（チャンクごとに独立して実行できる）かを静的に判定する                                                               | スクリプトの実行                            |
| `parallel`, `stream` | 順序つきチャンクストリーム、ワーカー、出力の順序つきマージ                                                                             | スクリプトの意味                            |
| `search`             | バイト・部分文字列検索（SSE2/AVX2、スカラー実装へのフォールバック付き）                                                                  | 正規表現                                |

## 正規表現エンジン

検索は最大3段階を通ります。後の段階ほど高価で、どの段階も NFA シミュレーションと完全に同じ結果を返します。

1. **リテラル先読み**（`regex::literal`）。リテラルだけのパターンは部分文字列検索で答えます。あるリテラルを必須とするパターン（単純なグループにまたがってもよい）は、それを含まない入力をオートマトンを動かす前に弾きます。
2. **遅延 DFA**（`regex::dfa`）。パターンに後方参照がなく、入力に区切り文字・改行バイトがないときに使います（UTF-8 ロケールでは、パターンの文字を UTF-8 のバイト列に展開して DFA をバイト単位で動かします。大文字小文字の畳み込みや単語アサーションを含むパターンは ASCII のみの入力に限ります）。前向きの非アンカー DFA が最も早いマッチ終端を見つけ、逆向き DFA（パターンを鏡写しにして構築）がそこで終わるマッチの最左の開始位置を見つけます。それより前の開始位置から始まるマッチは終端がより後ろになるはずなので、前向きのアンカー DFA を作業量の上限内で順に試し、最長の終端も前向きのアンカー DFA が求めます。状態は必要になったときに作ります（最大2000。超えたらフォールバック）。最初に最も早い終端を探すことで、長い1行に対する繰り返し検索も線形時間に収まります。
3. **NFA シミュレーションとバックトラック**（`regex::exec`）。基準となる実装です。後方参照、非 ASCII 入力、DFA が引き受けないものすべてを扱い、DFA が見つけた範囲に対して部分マッチを割り当てます。

DFA 経路は、ランダムなパターンと入力でシミュレーションと突き合わせ（`regex::tests`）、有効にした状態で fixture と実行 fuzz テストも通しています。

## ロケール

`locale::from_env` は、最初に一度だけ `setlocale(LC_ALL, "")` を呼び、`LC_CTYPE` の文字集合と、`LC_CTYPE`・`LC_COLLATE` の名前を読み戻します。結果は 3 つの `regex::Locale` のどれかで、文字を読むところはすべて、値を比べずに `Locale::is_utf8` で尋ねます。

| `Locale`   | 条件                                                                 | 文字とは何か、集合に何が入るか                                                                                         |
|------------|--------------------------------------------------------------------|---------------------------------------------------------------------------------------------------------|
| `C`        | バイト単位：`C`、`POSIX`、インストールされていない名前、UTF-8 以外の文字集合                     | 1 バイト。クラスは ASCII のみ                                                                                     |
| `Utf8`     | `LC_CTYPE` が `C.UTF-8` で、`LC_COLLATE` が `C`、`POSIX`、`C.UTF-8` のどれか | UTF-8 の 1 文字。`C.utf8` の表を組み込み済み（`classes_table`、`tools/gen-classes.py` で生成）。範囲はコードポイント順。マッチ中にライブラリを呼ばない |
| `Libc`     | それ以外の UTF-8 ロケール                                                   | UTF-8 の 1 文字。以下の問い合わせは C ライブラリに任せる                                                                      |

`Libc` では、答えがロケールに依存するとき、パーサーは `lib` を持つ `CharSet` を作り、`CharSet::matches_char` がライブラリに尋ねます。

- 範囲・クラス・等価クラス・照合記号を含むか、`I` の下で読まれるブラケット式は、全体を `regcomp` でコンパイルし（エラーコードは GNU sed のメッセージ `Invalid range end`、`Invalid collation character` などになります）、1 文字ずつ `regexec` で試します。答えは覚えておくので（ASCII は 2 つのビットマスク、それ以外は表）、テキストごとに、異なる文字 1 つにつきライブラリを 1 回呼ぶだけです。GNU sed と同じことをするので、範囲は `LC_COLLATE` の照合順序に、クラスと大文字小文字は `LC_CTYPE` に従い、自前でモデル化するものはありません。
- 単一の文字と ASCII 数字の範囲だけを持つブラケット式があるパターンは、その範囲をコードポイントとして読む形でもう一度コンパイルします（GNU sed の最初のマッチャーがそうします）。この読み方でマッチしないレコードにはマッチせず（`Regex::filter`）、通ったレコードの中のマッチはライブラリのものです（`echo 3٣ | sed 's/[0-9]/N/g'` は `NN`、`echo ٣ | sed 's/[0-9]/N/'` は `٣` を出力します）。
- `I` の下では、リテラルの文字や単一の文字だけのブラケット式は、パターンがその文字自体を書かない限り U+1C80..U+1C88 を取りません（GNU sed の最初のマッチャーについて観察した規則です）。
- `\w`、`\W`、`\s`、`\S` はライブラリにとって `[_[:alnum:]]` と `[[:space:]]` です。単語アサーションは `iswalnum` を使います。
- `I` の下のリテラルの文字は、`REG_ICASE` を付けた `regcomp` でコンパイルし、同じように尋ねます（`tr_TR.UTF-8` では `i` は `İ` と、`I` は `ı` と組になります）。`I` の下の後方参照と `\U \L \u \l` は `towupper`/`towlower` を使います。

`lib` を持つ集合は DFA には不透明です（`expand_utf8` は断ります）。そのため、そのようなパターンは ASCII のヘイスタックでは DFA、それ以外では NFA シミュレーションで動きます。既定の経路は影響を受けません。

**ほかの文字集合を足すとき**（EUC-JP、Shift_JIS、GBK、Big5、EUC-KR、ISO-8859-x、KOI8-R、Windows-125x のような単バイト集合）、問い合わせは変わりません。ライブラリは、どのロケールについてもすでに答えられます（`regcomp` と `iswalnum` は `wchar_t` を扱い、glibc ではどの文字集合でも Unicode です）。新しく要るのは、文字の読み書きです。ロケールにデコーダーを持たせ（ある位置の文字を `mbrtowc` で読む。`\U` の出力、`y`、DFA のバイト列のためにはその逆。状態を持つ集合や自己同期しない集合ではバイト列を書き出せないので、そうしたパターンはシミュレーションを使います）、単バイト集合は、256 バイトぶんのクラス表と大文字小文字の表をライブラリを呼んで埋めたバイト集合にします。拡張する場所は `Locale::is_utf8` と、`Locale` で分岐している箇所（`regex::parse`、`regex::exec`、`runtime::case`、`runtime::translate`、`syntax::parser` の区切り文字の検査）です。

## 方針

- CLI と Rust API は同じ経路（パースしてから実行）を共有します。大きな通常ファイルに対するレコード内完結のスクリプトは、順序つきチャンクストリーム上で並列に実行し、それ以外は逐次 VM で実行します。
- 未対応構文はコンパイル時エラーとし、黙って別の意味に解釈しません。
- 入力はバイト列として保持します。レコード末尾の区切りは本文と区別して扱います。
