# GNU sed 4.9 との既知の差分

ripgsed は GNU sed 4.9 と同じように動作します（同じ出力、C ロケールでの同じエラーメッセージ、同じ終了状態。[DECISIONS.md](DECISIONS.md) の D4）。GNU sed の挙動が C ライブラリの正規表現マッチャーの明らかなバグである場合、ripgsed は既定では定義どおりの結果を返し、`--glibc-compat` を付けたときだけそのバグを再現します（D10）。このオプションは、まったく同じ出力を保つ必要がある既存の GNU sed 資産を移行するためのもので、それ以外では不要です。このページでは、差分と、オプションが再現する内容を挙げます。

## 意図的な差分

- `--version` と `--help` は ripgsed 独自の文面を出します。usage の先頭行とオプションエラーの `sed:` の行は GNU sed と同じです。
- C ライブラリが持つ文字集合はすべて従います。UTF-8、マルチバイトの EUC-JP、Shift_JIS、GBK、GB18030、Big5、EUC-KR、EUC-TW（文字は `mbrtowc` で読みます）、ISO-8859-x、KOI8-R、Windows-125x などの単一バイト集合です（D11）。クラス、大文字小文字の規則、範囲の順序はロケールのもので、GNU sed と同じです。バイト単位で読むのは、インストールされていないロケールと `C`・`POSIX` だけです。GNU sed と比べていない集合（Big5-HKSCS、JIS X 0213 の系統）も同じコードを通るので動くはずですが、確かめてはいません。GB18030 と EUC-TW（4 バイトの文字）は、`tools/locale-diff.py --sample` で第 1・第 2 バイトの標本を GNU sed と比べました。
- 2 GiB 以上の1レコード：GNU sed は、そのレコードに対して正規表現を照合するとき、`regex input buffer length larger than INT_MAX`（終了状態 4）で止まります。C ライブラリがバッファの長さを `int` で数えているためです。ripgsed にはこの制限がなく、処理を続けます（GNU sed 4.9 で、改行のない 2,147,483,647 バイトの疎ファイルを使って測定。GNU sed は約 4 GiB のメモリを使いました）。それだけのメモリが要るので、fixture はありません。
- メモリ使用量は多めです。入力を 256 KiB のブロック単位で読み、並列実行では複数のブロックを同時に保持します。

## grep モード

grep モードは GNU grep 3.12 と比べています（D12）。GNU grep 3.11 は、試したすべての場合で同じ結果を返しますが、3.12 でなくなった下記のオプションだけは別です。

- `--version` と `--help` は ripgsed 自身の文面を出力します（使い方のメッセージとオプションの一覧は同じで、最後の行が違います）。`-u` と `--unix-byte-offsets` は GNU grep 3.12 にないオプションなので、ここでもエラーになります。
- GNU grep の翻訳済みメッセージ（`LANGUAGE=ja`）は使えません。そのカタログは GPL の下にあり、GNU sed のものと同じです（英語のメッセージは同じです）。PCRE2 ライブラリのメッセージはライブラリのものです。
- `-P` はシステムの PCRE2 ライブラリを使うので、結果もメッセージも、入っている版に従います。ライブラリがなければ、`-P` はメッセージを出して失敗します。
- GNU grep の DFA と C ライブラリのマッチャが食い違うパターンは、行を選ぶときと一致を探すときで、両方の読み方で読みます。再現しないもの。`-w` と `-x` は DFA に構文として適用されます（追加したグループを閉じる `)` の文字）。そのため、対応のない `)` を持つパターンは、`-w` や `-x` の下で別の行を選ぶことがあります。`((a{256}){256})` のような巨大な入れ子の繰り返しでの `grep: stack overflow`。sed モードが挙げる C ライブラリのマッチャの癖（`a?(a+)+\1`、`(c+){0,2}` のグループ）。これらは GNU grep にもあります。
- バイナリとエンコーディングの規則は、GNU grep が読む塊に従います。パイプでは各読み込みの大きさが決め、それは固定ではないので、パイプの後ろのほうに NUL があると、その前の行が、GNU grep とは別の場所からバイナリのデータになることがあります。
- 読めないファイルやディレクトリについてのメッセージのファイル名は、オペランドで与えられたものです。ディレクトリのファイルの順序はファイルシステムのもので、GNU grep と同じです。

## `--glibc-compat` で再現する glibc の挙動

GNU sed は C ライブラリの正規表現マッチャーを使っています。そのマッチャーが仕様にない動きをする場合、`--glibc-compat`（または環境変数 `RIPGSED_GLIBC_COMPAT=1`）を付けると、ripgsed も同じ動きをして、スクリプトが同じ出力になります。付けない場合は、定義どおりの結果（最左最長、後方参照は定義どおり）になります。差分テストと fixture は GNU sed の結果を保持しているので、このオプションを付けて実行します。

- パターンが1文字の繰り返し（`b*`、`[ab]*`、`(a*)*`、`a*\+`）で始まり、その直後に `\B` がある場合、その位置で繰り返しが1文字を消費できるときの空マッチは、その文字の後ろで報告されます。`echo ab | sed 's/b*\B/<&>/'` は `a<>b` ではなく `ab<>` を出力します。バッファの先頭では起きず、`\b`、`\<`、`\>` にも当てはまりません。fixture は `rgx-039` です。
- 繰り返しの中にあるグループへの後方参照は、POSIX が許す値のすべてを見るわけではありません。上限のある繰り返し `X{m,n}`（`?` は `{0,1}` で、`+`、`*`、`{m,}` は上限なしです）はグループのコピーに展開され、グループが見えるのは `m` 回か `n` 回の繰り返しの後だけです。`echo aaa | sed -E 's/(a){1,3}\1/<&>/'` は `<aaa>` ではなく `<aa>a` を出力します。さらに、あるコピーの値は、同じグループの別のコピーも同じ位置で終われるとき、見えません。ただし、その別のコピーが、より前のコピーで開始が同じか早いもの、またはより後ろのコピーで開始が遅いものである場合です。`aaaa` に対する `(a+)+\1` は `aa` にしか一致せず、`(a|aa){2}\1` は `aaa` に一致しませんが `aaaa` には一致し、`(a*){2}\1` はどこにも一致しません。例外が2つあります。グループの本体が空になれない場合、繰り返しの任意のコピーの中にあるコピーは、開始が同じ必須のコピーに妨げられません。本体が空になれる場合、必須のコピーは、後ろの任意のコピーに妨げられません。コピーがどこから始まりうるかは、マッチの先頭からパターンを後方参照を見ずにたどって求めます。対象は長さ 256 バイトまでのマッチと、コピーが 16 個までのグループです。fixture は `rgx-040` です。
- グループがループ（`*`、`+`、`{m,}`）の本体そのもので、空になれる場合、空になった最後の繰り返しは、後方参照からは空のグループに見えます。ただしグループの報告値は、空でない最後の繰り返しの値です。`echo a | sed -E 's/(a?)*\1/<&>[\1]/'` は `<a>[a]` を出力し、`(a*)*\1b` は `ab` 全体に一致します。上のコピーの規則は、この空の繰り返しにも当てはまります。そのため `(a?)+b\1` は `aab` 全体に一致しますが、`ab` では `b` だけに一致します。グループの本体がそれ自体繰り返し（`(a*)*`）の場合、グループは空として報告され、一致の終端に届く経路のうち、空でない繰り返しの後に空の繰り返しを含まない最初のものがレジスタを決めます（`aa` に対する `(a*)*\1` は `<aa>[a]` を出力します）。fixture は `rgx-041` と `rgx-012-backref-group-in-star-iteration` です。
- 後方参照が一致の先頭で空のグループを受け付けないために GNU sed の最初の試行が失敗すると、あとの位置で一致するはずでも、検索全体が失敗します。`(a?){2}\1` は `baaa` に一致せず（`aaa` には一致します）、`(a?){2}\1b` は `baaab` に一致しません。先頭でない位置で空のグループが受け付けられない場合は、そうなりません（`b(a?){2}\1` は `bbaaa` の `baaa` に一致します）。fixture は `rgx-041` です。
- 空になりうるグループへの後方参照で、マッチの開始位置で別の選択肢がそのグループを未設定のままにした場合も、glibc は検索全体を失敗させます（`echo ' yy' | sed -E 's/(\<()|())\2/<&>/'` は ` yy` を出力します。空の選択肢が先頭でマッチするはずですが、次の単語の先頭でのマッチは探されません）。パターンにアサーションがあり、先頭で見つかったマッチが空のときは、グループを未設定のままパターンの終わりに達する経路があるだけで検索が失敗します（`b` に対する `(\<()|())\2` は `b` を出力します）。フィクスチャは `rgx-044` です。
- 相対リンクの先が長くてパスが長くなりすぎる場合：GNU sed は連結したパスを固定長のバッファに入れて切り詰めます（GNU sed 4.9 での実測では、上限は 121 バイト。ディレクトリ部が 121 バイトより長ければ 185 バイト、それよりさらに長ければディレクトリ部だけ）。そのため `--follow-symlinks` は別のパスを読んだり編集したりします（`couldn't edit ...: not a regular file`）。既定では、パス全体を使います。fixture：`cmd-059`。
- マルチバイトの文字集合（EUC-JP、Shift_JIS、GBK、GB18030、Big5、EUC-KR、EUC-TW）で、`\U` や `\L` が文字をその集合に書けない文字へ変換すると、GNU sed は `case conversion produced an invalid character` と出力して異常終了します（シグナル。バッファされた行は出力されません）。既定ではその文字をそのまま残します。`tools/locale-diff.py` で GBK と EUC-JP のすべての 2 バイト列について確かめています。
- `I` の下の否定括弧式（`[^a-z]`）は、GBK（0xfe61〜0xfe6f）、Shift_JIS（0x8461〜0x846f、0x9873〜0x987a）、EUC-TW（第 4 面の 4 バイトコード 65 個）の未割り当てコードの一部を、`mbrtowc` が拒むにもかかわらず 1 文字として取ります。既定では、そのような列は文字ではありません。該当する列はライブラリに尋ねて見つけます（`locale::icase_seq`。2〜4 バイトで、最も長いものが勝ちます）。それらの集合のすべての列について確かめています。
- 複数の書き方がある文字（EUC-TW：第 1 面の文字は 2 バイトでも、面の接頭辞付きの 4 バイトでも書けます）は、括弧式の中では、ライブラリと同じく、その文字が書かれているバイト列で調べます。`wcrtomb` が作るバイト列では調べません。`[[=a=]]` は、`8e a1 a4 c1` と書かれた全角の `Ａ` を含みません。これは常に有効です。
- 照合記号から始まる範囲（`[[.a.]-z]`）は、Big5 の 8 コード（0xf9e9〜0xf9eb、0xf9f9〜0xf9fd）と、0x8e で始まる EUC-TW の 4 バイト文字の先頭バイトだけを取ります。`mbrtowc` ではこれらは 1 文字です（`printf '\xf9\xe9\n' | sed 's/[[.a.]-z]/X/'` は `X` と 2 バイト目を出力します）。既定では ripgsed はこれらを 1 文字として読みます。オプションを付けると、マッチは文字の途中で終わり、残りの部分（尾）はどのユニットにもマッチせず、空マッチのあとは 1 バイト進みます。ライブラリに尋ねて見つけ（`LibSet::partial_len`）、`tools/locale-diff.py` で Big5 と EUC-TW について確かめています。
- `I` の下で、大文字が元の文字よりバイト数の多い 1 文字のグループへの後方参照は、glibc では同じ文字にマッチしません。`echo ɐɐ | sed 's/\(.\)\1/X/I'` は `ɐɐ` を出力します（`ɐ` は 2 バイト、`Ɐ` は 3 バイト）。トルコ語のロケールでは `echo ii | sed 's/\(i\)\1/X/I'` が `ii` を出力します（`i` は 1 バイト、`İ` は 2 バイト）。`ɐⱯ` と `iİ` はマッチします。既定では、定義どおりのマッチになります。この規則は、`C.UTF-8` で大文字が長い 20 文字と、GB18030 の 32 文字（0xa8a1〜0xa8bf。大文字は 4 バイト）にちょうど当てはまることを、全コードポイントで確かめています。
- UTF-8 の文字のような構造をしているが文字ではないバイト列は、glibc のマッチャでは一部の場所でだけ 1 文字として読まれ、その前に GNU sed の最初のマッチャが判断します。U+10FFFF を超える並び（`F4 90 80 80`。最大 6 バイト）は、どのクラスにも属さない文字で、`.`、`\W`、`\S`、`[^a]`、`[^[:alpha:]]`、`[^[:print:]]`、`[^[:space:]]` が取り、`\b`、`\B`、`\>` では単語構成文字ではない文字です。符号化されたサロゲート（`ED A0 80`）は、GNU sed が多バイト対応と見なす集合（端点の間に書いた範囲。`[a-a]` や `[0-9]` も含む。クラス、否定の集合、`\\w`、ASCII でない文字、単語アサーション）がなく、`I` もないパターンで、しかも最初のマッチャが行を通すときに限って、`.` が取ります。`s///g` で空マッチのあと、そのような集合か `I` があるパターンでは並び全体（有効な文字なら 1 文字全体）を飛ばして進み、なければバイトごとに進みます。サロゲートは常にバイトごとです。最初のマッチャは、パターンを次のように読みます。判断できない集合（端点の違う範囲、数字以外のクラス、否定の集合、`\w`、`\s`）、すべての後方参照、すべての単語アサーションを「任意のバイト列（0 バイト以上）」とし、リテラル、列挙の集合（`[ab]`）、端点が 1 つの範囲（`[a-a]`）、ASCII の数字の集合（`[0-9]`、`[[:digit:]]`）はそのままにして、`.` にはそのような並びを取らせません。その読み方で行のどこかにマッチしたときだけ、パターンを glibc の読み方でもう一度実行し、そちらがマッチを見つけます。そのため、`a`、並び、`b` に対する `s/./X/g` は `XXX` ですが、そのような並びだけの行は変えません。`s/[a-z]./X/` は `a` と並びを取り、`s/[a-z].b/X/` は取らず（最初の読み方で `.` は並びを通れず、ほかに代わるものもない）、`s/[a-z].*b/X/` は取ります。ripgsed は、そのような並びがある行に対して同じことをします（`Regex::relaxed`、`charset::with_ext`）。オプションなしでは、並びはどこでも不正バイトです。フィクスチャは `loc-014-sequences-beyond-unicode` と `loc-014-first-matcher-and-bracket-then-dot`（GNU sed での 47 個の実験。ライセンスの規則を守ってライブラリを読む別の担当に尋ねて見つけ、ここで確かめたもの）です。15 種類の並び、28 のパターン、3 つの文脈の 2,520 回の比較に差はありません（2 段階の読み方がないと 380 通り）。
- 常に有効で、オプションではないもの：`C.UTF-8`（以下の表のロケール）でもほかの UTF-8 ロケールでも、クラスに何が入るか、文字の大文字小文字がどう変わるか、範囲が端をどう並べるかは、ロケールのものであり、修正した挙動にはなりません（D10、D11）。`C.UTF-8` では、文字クラス（`[[:alpha:]]`、`\w` など）は glibc の `C.utf8` の表に従います。表は C ライブラリから生成しており（`tools/gen-classes.py`）、Rust の標準ライブラリではなく glibc の Unicode バージョンに従います。

## `--glibc-compat` を付けても再現しない glibc の挙動

glibc のマッチャーが、最左最長の規則や後方参照の定義と食い違う結果を返す場合です。差分テスト（`tests/regex_differential.rs`）のランダムなパターンの約 0.06% が該当しますが、通常のパターンでは起きません。ripgsed は定義どおりの結果を返します。

| パターン（ERE）    | 入力      | glibc                   | ripgsed              |
|--------------|---------|-------------------------|----------------------|
| `a?(a+)+\1`  | `aaaaa` | `aaaaa` に一致、`\1` は `aa` | `aaa` に一致、`\1` は `a` |
| `a?(a?)+\1`  | `aa`    | `aa` に一致、`\1` は空        | `aa` に一致、`\1` は `a`  |
| `((a?)*)x\1` | `x`     | 一致なし                    | `x` に一致              |

1つ目は、繰り返しの中にあるグループへの後方参照で、繰り返しより前に空になれる部分があり、コピーの規則では足りないものです。`a?` が `a` を1つ取ると、グループの値はどの長さでも見え、`a?` が空のときは最短のものだけ見えます。2つ目は、`\1` が一方の経路で一致し、グループの報告が別の経路から来るものです。3つ目は、空になれるグループの繰り返しを含むグループで、GNU sed の答えは一致なしか文字化けです。固定幅のグループ（`(ab)+\1`）は仕様どおりに動きます。重ねた量指定子の下のキャプチャ（`((b?)+*|c){1}`）や、パターンの先頭でない繰り返しの後ろの `\B` でも差が出ることがあります。一覧上の項目は `compat/sed.tsv` の RGX-009 と RGX-012 です。

`-z` のとき、パターンの先頭の `$` に否定の括弧式が続くと、一致が消費する改行の手前でも `$` が成り立つことがあります。`a_`、改行、` aAcB` を `-z -E 's/$[b-c]*[^ c]*/<&>/g'` に通すと、GNU sed は改行に一致し、ripgsed は一致しません（レコードの末尾でない `$` が、そこで成り立つ理由はありません）。改行を消費したものの後ろの `^` でも同じことが起きます。`-z -E 's/\W^/<&>/g'` で、GNU sed は `a`、改行、`a` の改行に一致します。どちらもランダムなパターン約2300件のうち1件ほどで見つかりました。

## 再現していない C ライブラリの UTF-8 の挙動

- Unicode を超える並びやサロゲートを含む行に対するランダムなパターン（12,000 パターン、4 つの seed、2 ロケール。GNU sed との比較）には、食い違うものがありません。上の読み方がないと 16〜18% が食い違います。この読み方は観察したことのモデルなので、テストが引かなかった形のパターンでは、まだ食い違うかもしれません。
- `I` フラグのとき、glibc はパターンの文字と入力を一方向にだけ照合します。`s/В/X/I` は同じ大文字に畳まれる `U+1C80` に一致せず、`[µ]` は `Μ` と `μ` に一致します。ripgsed はリテラルを大文字に畳んで双方向に、ブラケットは各文字の 2 つの大小で照合します。ほかの UTF-8 ロケールでは、`I` の下の文字やブラケット式は C ライブラリのものです。小さなキリル文字の異体字 U+1C80..U+1C88 がそれ自身にしか取られないという GNU sed 自身の規則が 1 つあり（D11）、こうしたことは起きません。
- `a`、`i`、`c` のテキストが `\c` で終わるとき、GNU sed は付け足す改行をその制御文字として取り込みます（`a x\c` は `xJ` を書きます）。
- 無効な照合記号で始まり、クラスで終わる範囲（`[[.space.]-[:alpha:]]`）は、ripgsed では `Invalid collation character`、GNU sed では `Invalid range end` です。
- `--follow-symlinks` でシンボリックリンクの指すディレクトリを読むとき、読み取りエラーには ripgsed は指す先の名前を出します。GNU sed 4.9 はリリース tarball からビルドしたものがリンクの名前、パッケージ版が指す先の名前を出します。

## 再現していない、ほかの文字集合の挙動

集合のすべてのバイトと 2 バイト（EUC-JP は 3 バイトも）の列（`tools/locale-diff.py`）、およびランダムなパターン（`tools/locale-fuzz.py`）を比べて見つけたものです。集合の文字でない列か、特殊なパターンに限ります。

- GB18030 で `I` の下では、文字 0xa8a1〜0xa8bf（たとえば `[a-z]`、`[^0-9]`）に対する GNU sed の答えが、その周りのテキストによって変わり、実行ごとにも変わります（同じ入力で 40 回中 24 回は別の出力）。そのため合わせる対象がありません。valgrind で原因が分かりました。C ライブラリのマッチャ（glibc 2.39 の `regexec.c`、`check_node_accept_bytes` と `transit_state`）が、初期化していない値を読んでいます。ripgsed は、その文字だけを尋ねたときのライブラリの答えを返します。
- GNU sed は、そのロケールの言語パックが入っていれば、メッセージを翻訳して出します（Ubuntu の `ja_JP` で `LANGUAGE=ja` とすると、`sed: -e expression #1, char 1: ` とそれに続く文面が日本語で出ます）。翻訳されるのは、GNU sed 自身のメッセージ（そのカタログによる）と、不正な括弧式に対する C ライブラリのメッセージ（`Invalid range end` など。ライブラリのカタログによる）で、どちらもロケールの文字集合で出ます。ripgsed は、`C` ロケールと同じく英語の文面を出します（D11）。フィクスチャは `LANGUAGE=C` を設定しています。カタログは GNU の翻訳で、所属するパッケージのライセンスを持ちます。このプロジェクトは GPL のコードに由来するものをいっさい取り込まない方針なので（ARCHITECTURE.md の出所とライセンスを参照）、これは作業の限界ではなく、ライセンスの限界です。

## glibc への報告

上の後方参照と `\B` の例は、sed を使わず素の `regcomp`/`regexec`（`REG_EXTENDED`）でも再現します。

```c
regcomp(&re, "(a+)+\\1", REG_EXTENDED);   /* "aaaa": reports [0,2), the longest is [0,4) */
regcomp(&re, "(a*){2}\\1", REG_EXTENDED); /* "aaaaaa": no match, [0,6) is one */
regcomp(&re, "b*\\B", REG_EXTENDED);      /* "ab": reports the empty match at 2, not at 1 */
```

glibc 2.43（Ubuntu 2.43-2ubuntu2.4）で確認しました。glibc のバグトラッカー（コンポーネント `regex`）への報告では、POSIX が最左最長のマッチを求めていること、`\B` はマッチの位置で成り立たなければならないことを書きます。
