# GNU sed 4.9 との既知の差分

ripgsed は GNU sed 4.9 と同じように動きます。出力が同じで、C ロケールのエラーメッセージも同じで、終了状態も同じです（[DECISIONS.md](DECISIONS.md) の D4）。

- GNU sed の挙動が C ライブラリの正規表現マッチャーのバグであることが明らかな場合、ripgsed は既定では定義どおりの結果を返し、バグそのものは `--glibc-compat` を付けたときだけ再現します（D10）。
- このオプションは、すでにある GNU sed の資産を、まったく同じ出力のまま使い続けなければならないときのためのもので、それ以外では要りません。
- このページは、その違いと、オプションが再現するものを一覧にしたものです。

## 意図的な差分

- `--version` と `--help` は ripgsed 独自の文面を出します。usage の先頭行とオプションエラーの `sed:` の行は GNU sed と同じです。
- C ライブラリが持つすべての文字集合に従います。UTF-8、マルチバイト集合の EUC-JP、Shift_JIS、GBK、GB18030、Big5、EUC-KR、EUC-TW（文字は `mbrtowc` で読みます）、ISO-8859-x、KOI8-R、Windows-125x などの 1 バイト集合です（D11）。
  - クラス、大文字小文字の規則、範囲の順序は、GNU sed と同じくロケールのものです。
  - バイトとして読むのは、インストールされていないロケールと、`C` と `POSIX` だけです。
  - GNU sed と比べていない集合（Big5-HKSCS や JIS X 0213 の変種）も同じコードを通るので動くはずですが、それを確かめるものはありません。
  - GB18030 と EUC-TW（4 バイト文字）は、先頭バイトと 2 バイト目の標本を `tools/locale-diff.py --sample` で比べました。
- 2 GiB 以上の1レコード：GNU sed は、そのレコードに対して正規表現を照合するとき、`regex input buffer length larger than INT_MAX`（終了状態 4）で止まります。C ライブラリがバッファの長さを `int` で数えているためです。ripgsed にはこの制限がなく、処理を続けます（GNU sed 4.9 で、改行のない 2,147,483,647 バイトの疎ファイルを使って測定。GNU sed は約 4 GiB のメモリを使いました）。それだけのメモリが要るので、fixture はありません。
- メモリ使用量は多めです。入力を 256 KiB のブロック単位で読み、並列実行では複数のブロックを同時に保持します。

## grep モード

grep モードは GNU grep 3.11 と PCRE2 10.42 と比べています（D12）。3.12 で違う 4 つの点は、`src/grep/mod.rs` の `GNU_GREP_3_12` を切り替えて従います（docs/GREP.md に一覧と手順があります）。

- `--version` と `--help` は ripgsed 自身の文面を出力します（使い方のメッセージとオプションの一覧は同じで、最後の行が違います）。`-u` と `--unix-byte-offsets` は、3.11 と同じく警告を出します（3.12 からはエラーです）。
- GNU grep の翻訳済みメッセージ（`LANGUAGE=ja`）は使えません。そのカタログは GPL の下にあり、GNU sed のものと同じです（英語のメッセージは同じです）。PCRE2 ライブラリのメッセージはライブラリのものです。
- `-P` はプログラムと一緒にビルドする PCRE2 ライブラリ（この文を書いた時点で 10.46）を使うので、結果とメッセージはその版のものになり、GNU grep がビルドされた版とは違うことがあります。
- GNU grep の DFA と C ライブラリのマッチャーで違うパターンは、行にもマッチにも、両方の読み方で読みます。再現しないもの：
  - `-w` と `-x` は DFA に対して構文として適用されます（追加したグループを閉じる `)` のテキスト）。そのため、対のない `)` を持つパターンは、`-w` や `-x` の下で別の行を選ぶことがあります。
  - `((a{256}){256})` のような、巨大な入れ子の繰り返しでの `grep: stack overflow`。
  - sed モードが挙げる C ライブラリのマッチャーの癖（`a?(a+)+\1`、`(c+){0,2}` のグループ）。GNU grep にも同じものがあります。
- バイナリとエンコーディングの規則は、GNU grep が読む塊に従います。パイプでは各読み込みの大きさが決め、それは固定ではないので、パイプの後ろのほうに NUL があると、その前の行が、GNU grep とは別の場所からバイナリのデータになることがあります。
- 読めないファイルやディレクトリについてのメッセージのファイル名は、オペランドで与えられたものです。ディレクトリのファイルの順序はファイルシステムのもので、GNU grep と同じです。

## `--glibc-compat` で再現する glibc の挙動

GNU sed は C ライブラリの正規表現マッチャーを使っています。そのマッチャーが仕様にない動きをする場合、`--glibc-compat`（または環境変数 `RIPGSED_GLIBC_COMPAT=1`）を付けると、ripgsed も同じ動きをして、スクリプトが同じ出力になります。付けない場合は、定義どおりの結果（最左最長、後方参照は定義どおり）になります。差分テストと fixture は GNU sed の結果を保持しているので、このオプションを付けて実行します。

- パターンが1文字の繰り返し（`b*`、`[ab]*`、`(a*)*`、`a*\+`）で始まり、その直後に `\B` がある場合、その位置で繰り返しが1文字を消費できるときの空マッチは、その文字の後ろで報告されます。`echo ab | sed 's/b*\B/<&>/'` は `a<>b` ではなく `ab<>` を出力します。バッファの先頭では起きず、`\b`、`\<`、`\>` にも当てはまりません。fixture は `rgx-039` です。
- 繰り返しの中のグループへの後方参照は、POSIX が許すすべての値を見るわけではありません。
  - 回数が限られた繰り返し `X{m,n}`（`?` は `{0,1}`。`+`、`*`、`{m,}` は限られていません）は、グループのコピーに展開され、グループは `m` 回または `n` 回の繰り返しのあとにだけ見えます。`echo aaa | sed -E 's/(a){1,3}\1/<&>/'` は `<aaa>` ではなく `<aa>a` を出力します。
  - さらに、あるコピーの値は、グループの別のコピーも終わりうる位置では見えません。そのコピーが、開始が遅くない前のコピーか、開始が遅い後ろのコピーのときです。`aaaa` に対する `(a+)+\1` は `aa` にだけマッチし、`(a|aa){2}\1` は `aaa` にはマッチしませんが `aaaa` にはマッチし、`(a*){2}\1` は決してマッチしません。
  - 例外が 2 つあります。グループの本体が空にならないときは、繰り返しの省略できるコピーの中のコピーは、同じ位置から始まる必須のコピーに妨げられません。空になりうるときは、必須のコピーは、あとの省略できるコピーに妨げられません。
  - コピーがどこから始まりうるかは、後方参照を見ずにパターンをマッチの先頭から辿って調べます。対象は、256 バイトまでのマッチと、コピーが 16 個までのグループです。
  - フィクスチャ：`rgx-040`。
- グループが（`*`、`+`、`{m,}` の）ループの本体全体で、空になりうるとき、最後の繰り返しが空なら、後方参照はそれを空のグループとして見ます。ただしグループ自体は、最後の空でない繰り返しの値で報告されます。`echo a | sed -E 's/(a?)*\1/<&>[\1]/'` は `<a>[a]` を出力し、`(a*)*\1b` は `ab` の全体にマッチします。
  - 上のコピーの規則は、その空の繰り返しにも当てはまります。そのため `(a?)+b\1` は `aab` の全体にマッチしますが、`ab` では `b` だけにマッチします。
  - グループの本体自体が繰り返し（`(a*)*`）のときは、グループは空と報告されます。マッチの終わりに届く経路のうち、空でない繰り返しのあとに空の繰り返しが来ない最初の経路が、レジスタを与えます（`aa` に対して `(a*)*\1` は `<aa>[a]` を出力します）。
  - フィクスチャ：`rgx-041`、`rgx-012-backref-group-in-star-iteration`。
- 後方参照が一致の先頭で空のグループを受け付けないために GNU sed の最初の試行が失敗すると、あとの位置で一致するはずでも、検索全体が失敗します。`(a?){2}\1` は `baaa` に一致せず（`aaa` には一致します）、`(a?){2}\1b` は `baaab` に一致しません。先頭でない位置で空のグループが受け付けられない場合は、そうなりません（`b(a?){2}\1` は `bbaaa` の `baaa` に一致します）。fixture は `rgx-041` です。
- 空になりうるグループへの後方参照で、マッチの開始位置で別の選択肢がそのグループを未設定のままにした場合も、glibc は検索全体を失敗させます（`echo ' yy' | sed -E 's/(\<()|())\2/<&>/'` は ` yy` を出力します。空の選択肢が先頭でマッチするはずですが、次の単語の先頭でのマッチは探されません）。
  - パターンにアサーションがあり、先頭で見つかったマッチが空のときは、グループを未設定のままパターンの終わりに達する経路があるだけで検索が失敗します（`b` に対する `(\<()|())\2` は `b` を出力します）。
  - フィクスチャは `rgx-044` です。
- 相対リンクの先が長くてパスが長くなりすぎる場合：GNU sed は連結したパスを固定長のバッファに入れて切り詰めます（GNU sed 4.9 での実測では、上限は 121 バイト。ディレクトリ部が 121 バイトより長ければ 185 バイト、それよりさらに長ければディレクトリ部だけ）。そのため `--follow-symlinks` は別のパスを読んだり編集したりします（`couldn't edit ...: not a regular file`）。既定では、パス全体を使います。fixture：`cmd-059`。
- マルチバイトの文字集合（EUC-JP、Shift_JIS、GBK、GB18030、Big5、EUC-KR、EUC-TW）で、`\U` や `\L` が文字をその集合に書けない文字へ変換すると（EUC-JP のコードセット 3 の 2 文字、GBK の 30 文字）、GNU sed は `case conversion produced an invalid character` と出力して異常終了します（シグナル。バッファされた行は出力されません）。
  - 既定ではその文字をそのまま残します。
  - `tools/locale-diff.py` で GBK と EUC-JP のすべての 2 バイト列について確かめています。
- `I` の下の否定括弧式（`[^a-z]`）は、GBK（0xfe61〜0xfe6f）、Shift_JIS（0x8461〜0x846f、0x9873〜0x987a）、EUC-TW（第 4 面の 4 バイトコード 65 個）の未割り当てコードの一部を、`mbrtowc` が拒むにもかかわらず 1 文字として取ります。既定では、そのような列は文字ではありません。該当する列はライブラリに尋ねて見つけます（`locale::icase_seq`。2〜4 バイトで、最も長いものが勝ちます）。それらの集合のすべての列について確かめています。
- 複数の書き方がある文字（EUC-TW：第 1 面の文字は 2 バイトでも、面の接頭辞付きの 4 バイトでも書けます）は、括弧式の中では、ライブラリと同じく、その文字が書かれているバイト列で調べます。`wcrtomb` が作るバイト列では調べません。`[[=a=]]` は、`8e a1 a4 c1` と書かれた全角の `Ａ` を含みません。これは常に有効です。
- 照合記号から始まる範囲（`[[.a.]-z]`）は、Big5 の 8 コード（0xf9e9〜0xf9eb、0xf9f9〜0xf9fd）と、0x8e で始まる EUC-TW の 4 バイト文字の先頭バイトだけを取ります。`mbrtowc` ではこれらは 1 文字です（`printf '\xf9\xe9\n' | sed 's/[[.a.]-z]/X/'` は `X` と 2 バイト目を出力します）。
  - 既定では ripgsed はこれらを 1 文字として読みます。
  - オプションを付けると、マッチは文字の途中で終わり、残りの部分（尾）はどのユニットにもマッチせず、空マッチのあとは 1 バイト進みます。
  - ライブラリに尋ねて見つけ（`LibSet::partial_len`）、`tools/locale-diff.py` で Big5 と EUC-TW について確かめています。
- `I` の下で、大文字が元の文字よりバイト数の多い 1 文字のグループへの後方参照は、glibc では同じ文字にマッチしません。`echo ɐɐ | sed 's/\(.\)\1/X/I'` は `ɐɐ` を出力します（`ɐ` は 2 バイト、`Ɐ` は 3 バイト）。トルコ語のロケールでは `echo ii | sed 's/\(i\)\1/X/I'` が `ii` を出力します（`i` は 1 バイト、`İ` は 2 バイト）。`ɐⱯ` と `iİ` はマッチします。
  - 既定では、定義どおりのマッチになります。
  - この規則は、`C.UTF-8` で大文字が長い 20 文字と、GB18030 の 32 文字（0xa8a1〜0xa8bf。大文字は 4 バイト）にちょうど当てはまることを、全コードポイントで確かめています。
- UTF-8 の文字のように作られているが、そうではないバイト列は、glibc のマッチャーが、場所によってだけ、1 文字として読みます。GNU sed の最初のマッチャーが、その前に判断します。
  - U+10FFFF を超えるバイト列（`F4 90 80 80`、最大 6 バイト）は、どのクラスにも含まれない文字です。`.`、`\W`、`\S`、`[^a]`、`[^[:alpha:]]`、`[^[:print:]]`、`[^[:space:]]` はそれを取り、`\b`、`\B`、`\>` にとっては単語でない文字です。
  - エンコードされたサロゲート（`ED A0 80`）は、`.` が取るのは、パターンに GNU sed がマルチバイト対応として扱う集合（両端を書いた範囲。`[a-a]` や `[0-9]` も含む。クラス、否定集合、`\w`、ASCII でない文字、単語アサーション）がなく、`I` もなく、最初のマッチャーがその行を通した場合だけです。
  - `s///g` で空マッチのあと、パターンにそのような集合か `I` があれば、検索はバイト列全体（と有効な文字全体）の後ろから続き、なければ 1 バイトずつ進みます。サロゲートは常に 1 バイトずつ進みます。
  - 最初のマッチャーは、判断できない集合（両端が違う範囲、数字以外のクラス、否定集合、`\w`、`\s`）、後方参照、単語アサーションを、すべて任意のバイト（0 個以上）として読みます。リテラル、列挙した集合（`[ab]`）、片端だけの範囲（`[a-a]`）、ASCII の数字の集合（`[0-9]`、`[[:digit:]]`）は保ち、`.` がそのようなバイト列を取らないようにします。
  - その読み方が行のどこかでマッチしたときだけ、パターンを glibc の読み方でもう一度実行し、その読み方がマッチを見つけます。
  - そのため、`a`、バイト列、`b` の行に対する `s/./X/g` は `XXX` を出力しますが、そのようなバイト列だけでできた行には何もしません。`s/[a-z]./X/` は `a` とバイト列を取りますが、`s/[a-z].b/X/` は取りません（最初の読み方では `.` がバイト列を通れず、ほかに代わるものがないため）。`s/[a-z].*b/X/` は取ります。ripgsed は、そのようなバイト列のある行で同じことをします（`Regex::relaxed`、`charset::with_ext`）。オプションがなければ、バイト列はどこでも不正なバイトです。
  - フィクスチャ：`loc-014-sequences-beyond-unicode`、`loc-014-first-matcher-and-bracket-then-dot`（GNU sed での 47 の実験。ライセンスの規則を念頭に、ライブラリの別の読み手に尋ねて見つけ、ここで確かめました）。15 種類のバイト列、28 のパターン、3 つの文脈の 2,520 回の比較で、違いは 1 つもありません（2 つの読み方がなければ 380）。
- 常に有効で、オプションではないもの：`C.UTF-8`（以下の表のロケール）でもほかの UTF-8 ロケールでも、クラスに何が入るか、文字の大文字小文字がどう変わるか、範囲が端をどう並べるかは、ロケールのものであり、修正した挙動にはなりません（D10、D11）。`C.UTF-8` では、文字クラス（`[[:alpha:]]`、`\w` など）は glibc の `C.utf8` の表に従います。表は C ライブラリから生成しており（`tools/gen-classes.py`）、Rust の標準ライブラリではなく glibc の Unicode バージョンに従います。

## `--glibc-compat` を付けても再現しない glibc の挙動

glibc のマッチャーが、最左最長の規則や後方参照の定義と食い違う結果を返す場合です。差分テスト（`tests/regex_differential.rs`）のランダムなパターンの約 0.06% が該当しますが、通常のパターンでは起きません。ripgsed は定義どおりの結果を返します。

| パターン（ERE）    | 入力      | glibc                   | ripgsed              |
|--------------|---------|-------------------------|----------------------|
| `a?(a+)+\1`  | `aaaaa` | `aaaaa` に一致、`\1` は `aa` | `aaa` に一致、`\1` は `a` |
| `a?(a?)+\1`  | `aa`    | `aa` に一致、`\1` は空        | `aa` に一致、`\1` は `a`  |
| `((a?)*)x\1` | `x`     | 一致なし                    | `x` に一致              |

1 つ目は、繰り返しの中のグループへの後方参照で、繰り返しの前に空になりうるものがあり、コピーの規則では足りない場合です。`a?` が `a` を 1 つ取れば、グループのすべての長さについて値が見えますが、`a?` が空なら、最短の長さだけです。

- 2 つ目は、`\1` がある経路でマッチし、グループは別の経路から報告される場合です。
- 3 つ目は、空になりうるグループのループを含むグループで、GNU sed の答えはマッチなしか、でたらめです。
- 固定幅のグループ（`(ab)+\1`）は、仕様どおりに動きます。
- 積み重ねた量指定子のキャプチャ（`((b?)+*|c){1}`）と、パターンの先頭でない繰り返しのあとの `\B` も、違うことがあります。
- マトリクスの項目は、`compat/sed.tsv` の RGX-009 と RGX-012 です。

`-z` のとき、パターンの先頭の `$` に否定の括弧式が続くと、一致が消費する改行の手前でも `$` が成り立つことがあります。`a_`、改行、` aAcB` を `-z -E 's/$[b-c]*[^ c]*/<&>/g'` に通すと、GNU sed は改行に一致し、ripgsed は一致しません（レコードの末尾でない `$` が、そこで成り立つ理由はありません）。

改行を消費したものの後ろの `^` でも同じことが起きます。`-z -E 's/\W^/<&>/g'` で、GNU sed は `a`、改行、`a` の改行に一致します。

どちらもランダムなパターン約2300件のうち1件ほどで見つかりました。

## 再現していない C ライブラリの UTF-8 の挙動

- Unicode を超える並びやサロゲートを含む行に対するランダムなパターン（12,000 パターン、4 つの seed、2 ロケール。GNU sed との比較）には、食い違うものがありません。上の読み方がないと 16〜18% が食い違います。この読み方は観察したことのモデルなので、テストが引かなかった形のパターンでは、まだ食い違うかもしれません。
- `I` フラグのとき、glibc はパターンの文字と入力を一方向にだけ照合します。`s/В/X/I` は同じ大文字に畳まれる `U+1C80` に一致せず、`[µ]` は `Μ` と `μ` に一致します。ripgsed はリテラルを大文字に畳んで双方向に、ブラケットは各文字の 2 つの大小で照合します。ほかの UTF-8 ロケールでは、`I` の下の文字やブラケット式は C ライブラリのものです。小さなキリル文字の異体字 U+1C80..U+1C88 がそれ自身にしか取られないという GNU sed 自身の規則が 1 つあり（D11）、こうしたことは起きません。
- `a`、`i`、`c` のテキストが `\c` で終わるとき、GNU sed は付け足す改行をその制御文字として取り込みます（`a x\c` は `xJ` を書きます）。
- 無効な照合記号で始まり、クラスで終わる範囲（`[[.space.]-[:alpha:]]`）は、ripgsed では `Invalid collation character`、GNU sed では `Invalid range end` です。
- `--follow-symlinks` でシンボリックリンクの指すディレクトリを読むとき、読み取りエラーには ripgsed は指す先の名前を出します。GNU sed 4.9 はリリース tarball からビルドしたものがリンクの名前、パッケージ版が指す先の名前を出します。

## 再現していない、ほかの文字集合の挙動

集合のすべてのバイトと 2 バイト（EUC-JP は 3 バイトも）の列（`tools/locale-diff.py`）、およびランダムなパターン（`tools/locale-fuzz.py`）を比べて見つけたものです。集合の文字でない列か、特殊なパターンに限ります。

- GB18030 で `I` の下では、文字 0xa8a1〜0xa8bf（たとえば `[a-z]`、`[^0-9]`）に対する GNU sed の答えが、その周りのテキストによって変わり、実行ごとにも変わります（同じ入力で 40 回中 24 回は別の出力）。そのため合わせる対象がありません。valgrind で原因が分かりました。C ライブラリのマッチャ（glibc 2.39 の `regexec.c`、`check_node_accept_bytes` と `transit_state`）が、初期化していない値を読んでいます。ripgsed は、その文字だけを尋ねたときのライブラリの答えを返します。
- 言語パックがインストールされていると、GNU sed はメッセージを翻訳します（Ubuntu で `LANGUAGE=ja` と `ja_JP`：`sed: -e expression #1, char 1: ` とそれに続く文が日本語で出力されます）。
  - これには、GNU sed 自身のメッセージ（そのカタログから）と、不正なブラケット式に対する C ライブラリのメッセージ（`Invalid range end` など。ライブラリのカタログから）があり、どちらもロケールの文字集合で出ます。ripgsed は `C` ロケールと同じく英語の文を出力し（D11）、fixture は `LANGUAGE=C` を設定します。
  - カタログは GNU の翻訳で、それが属するパッケージのライセンスを持ちます。このプロジェクトは GPL のコードに由来するものは何もコピーしません（ARCHITECTURE.md の Provenance 参照）。そのため、これは作業の限界ではなく、ライセンスの限界です。

## glibc への報告

上の後方参照と `\B` の例は、sed を使わず素の `regcomp`/`regexec`（`REG_EXTENDED`）でも再現します。

```c
regcomp(&re, "(a+)+\\1", REG_EXTENDED);   /* "aaaa": reports [0,2), the longest is [0,4) */
regcomp(&re, "(a*){2}\\1", REG_EXTENDED); /* "aaaaaa": no match, [0,6) is one */
regcomp(&re, "b*\\B", REG_EXTENDED);      /* "ab": reports the empty match at 2, not at 1 */
```

glibc 2.43（Ubuntu 2.43-2ubuntu2.4）で確認しました。glibc のバグトラッカー（コンポーネント `regex`）への報告では、POSIX が最左最長のマッチを求めていること、`\B` はマッチの位置で成り立たなければならないことを書きます。
