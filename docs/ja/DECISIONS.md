# 決定事項

これまでに決めたことと、その理由です。提案と未決の事項は [DESIGN.md](DESIGN.md) に置きます。決定は見直せますが、黙って消さずに、変更をここに記録します。

## D1. ライセンス：`MIT OR Apache-2.0`

- このプロジェクトは独立実装で、Rust のエコシステムで一般的なデュアルライセンスの `MIT OR Apache-2.0` でライセンスします。
- GPL のコードに由来するものは追加しません。GNU sed と GNU grep は参照としてだけ読み、コピーしません（DESIGN.md の由来の方針を参照）。

## D2. 入力表現：バイト列

- 入力、pattern space、hold space、出力は `String` ではなくバイト列です。GNU sed との完全互換には、不正な UTF-8 と NUL を受け付ける必要があります。
- レコード末尾の区切り（LF または NUL）は、レコード本文と別に保持します。最終改行がないことは保持し、正規化しません。
- P0 の対象は `C` ロケールのみで、`LC_ALL=C` の GNU sed と一致するバイト単位の挙動です。マルチバイトの文字単位の挙動（たとえば `.` が 1 文字にマッチする）は後の段階であり、それまでは達成したと主張しません。
- 入力はバッファ付きのストリームで読みます。メモリはファイル全体のサイズではなく、単一レコードの長さに応じて増えます。

## D3. 正規表現はエンジンの抽象化の裏に置く

- コアは正規表現ライブラリを直接呼びません。エンジンのインターフェース（DESIGN.md の「エンジンの抽象化」を参照）を使うので、このプロジェクト自身のエンジン（D7）と、opt-in の拡張としての PCRE2 などのエンジンを、並べて置けます。
- エンジンは（構文方言とオプションにより）明示的に選び、未対応の構文があっても黙って切り替えません。

## D4. GNU sed の完全互換は最低要件

- GNU sed と完全に互換になるまで、ripgsed は `sed` の代替としてリリースも説明もしません。完全互換とは、有効な GNU sed の呼び出しのどれに対しても、同じ stdout、終了状態、ファイルへの影響を返すことです。意図的に異なるのは、バージョン表記とヘルプの文面だけです（DESIGN.md を参照）。
- P0 のようなマイルストーンは作業の順序であり、小さな製品ではありません。この要件に関して、部分集合を「完了」と見なすことはありません。
- したがって範囲は、GNU sed のマニュアルにあるすべてです。すべてのコマンド、オプション、フラグ、エスケープ、アドレス形式、特殊なケースを含みます。互換性の一覧は最初からそれらをすべて挙げ、それぞれを未対応・部分対応・検証済みのいずれかとして記録し、未対応のものはコンパイル時エラーにします。
- 範囲には、マルチバイトと UTF-8 ロケールの挙動（D2 は作業の順序を決めただけで、まず `C` ロケール）と、`--debug` が明示的に含まれます。`--debug` の正規形のプログラム表示と実行の注釈も、ほかの出力と同様に GNU sed と比較します。
- 互換性は、GNU sed との差分テスト（リポジトリの tests/README.md を参照）でのみ検証し、主張だけで済ませることはありません。
- grep モードは、sed モードの後に、GNU grep について同じ水準を目指します。

## D5. 終了状態とエラーメッセージは GNU sed と完全に一致させる

- 終了状態は、文書化された 0・1・2・4 や `q`・`Q` に与えるコードを含め、すべての場合で GNU sed と同一です。
- stderr に出すエラーと警告のメッセージは、`C` ロケールの GNU sed のメッセージと一字一句同一です。`-e expression #1, char 3:` のような位置の部分も含みます。
- 呼ばれた名前に従うのはプログラム名の接頭辞だけです。`sed` として実行すれば `sed:`、`ripgsed` として実行すれば `ripgsed:` になります。これは名乗り方を意図的に変えたことの帰結であり、互換性の例外ではありません。
- gettext で他の言語に翻訳されたメッセージは、互換性の一覧のロケールの項目に属し、英語のメッセージの後に対応します。
- 差分テストは、stdout と終了状態に加えて stderr も比較します。

## D6. 互換の基準：GNU sed 4.9

- 挙動と、生成するテストの期待値の基準は、執筆時点で最新の安定版である GNU sed 4.9 です。
- 新しい GNU sed で変わった挙動は、黙って追従しません。互換性の一覧に別項目として記録し、基準のバージョンは改めて決めます。
- `--version` が出力するバージョン行には、この基準を明記します（DESIGN.md を参照）。

## D7. 正規表現エンジンは自前で書く

- つなぎとしても、サードパーティの正規表現ライブラリは使いません。POSIX の左端最長一致、後方参照、GNU 拡張を備えた GNU sed の BRE と ERE を、最初のリリースからこのプロジェクト自身のエンジンで実装します。
- 方言には、既定の GNU の挙動だけでなく、BRE と ERE の `--posix` と `POSIXLY_CORRECT` の変種、およびロケールが含まれます（D2 は作業の順序を決めたもので、まず `C` ロケール、その後に UTF-8 などのマルチバイトロケール）。
- 仕様は、GNU sed 4.9（D6）の観測できる挙動であり、POSIX と異なる箇所も含みます。その挙動は、GNU sed との差分テストが決めます。
- エンジンは D3 のインターフェースの裏にあるので、単独でテスト、ベンチマーク、ほかのエンジンとの比較ができます。

## D8. 対応プラットフォームとツールチェーン

- 最初に対応するプラットフォームは Linux です。差分テストは POSIX の `sh`、シンボリックリンク、参照としての GNU sed 4.9 に依存するため、Unix 系でのみ動きます。ほかのプラットフォームは、コアの検証が済んでから対応します。
- 対応する最小の Rust のバージョンは 1.85 で、edition 2024 を最初に備えたリリースです。`Cargo.toml` で宣言します。必要な機能があるときだけ引き上げ、その旨をここに記録します。
- いまのところ、サードパーティの依存はありません（正規表現は D7 を参照）。依存を足すときは、その理由をここに記録します。

## D9. 速さは中核の目標：GNU sed 4.9 に勝つ（測定して）

- GNU sed 4.9 より速いことは、完全互換（D4）と並ぶこのプロジェクトの目標です。互換性が先で、どの最適化も出力を変えてはならないため、すべての変更は、差分 fixture とランダム差分テストを通し続ける必要があります。
- 「速い」は `tools/bench.sh` で定義します。決まった再現可能な workload（リテラルと正規表現の置換、アドレス照合、`y`、複数行サイクル、巨大な 1 行）を、同じマシンで GNU sed 4.9 と比べ、出力の一致をハッシュで確認します。主張にはマシン、ビルド、数値を添え、測っていない主張はしません。
- 作業は見込める効果の順に進めます。正規表現の探索（リテラルの先読み、後方参照のないパターンの DFA）、割り当てと I/O のオーバーヘッド、そして静的解析でレコード内で完結すると証明できたスクリプトの自動並列実行（DESIGN.md）です。それ以外は逐次にフォールバックします。
- 最初のリリースは、完全互換でベンチマークでも速くなるまで `sed` の代替とは呼びません。差が残るなら、数値の隣にその差を正直に書きます。

## D10. 完全互換。ただし C ライブラリの正規表現のバグは要求されたときだけ

- GNU sed 4.9 との互換性（D4）には3つの水準がある。(1) 文書化された、意図された挙動は、常に GNU sed と同じ。(2) 明らかなバグである挙動は、既定では修正された挙動、つまり定義どおりの結果にする。(3) バグそのものは、`--glibc-compat`（または `RIPGSED_GLIBC_COMPAT=1`）を付けたときだけ再現する。これは、まったく同じ出力を保つ必要がある既存の GNU sed 資産を移行するためのもの。
- 挙動がバグと見なされるのは、次のいずれかを満たす場合に限る。GNU sed のマニュアルか POSIX に反している。上流（glibc、GNU sed）が不具合と認めている。新しい版で修正されている。それ以外は挙動として扱い、水準 (1) に残す。
- 最初の例は、glibc の正規表現マッチャーの癖である。先頭の繰り返しの後ろにある `\B` の前の空マッチと、繰り返しの中のグループへの後方参照の不完全な探索（docs/KNOWN-DIFFERENCES.md）。`C.utf8` の文字クラス表はロケールの実装であって癖ではなく、常に有効にする。
- 差分テストと fixture は GNU sed と比較するので、オプションを付けて実行する。既定側は、定義どおりの結果を明記したテストで確かめる。互換性一覧（`compat/sed.tsv`）では、オプションを付けたときに GNU sed と一致する項目を verified とする。
- オプション名は、GNU sed の長いオプションの接頭辞を避けている（`--regex...` だと `--regexp-extended` の短縮形が曖昧になる）。

## D11. ロケールは C ライブラリのもの

- GNU sed はロケールのことを C ライブラリ（`setlocale`、`towupper`、`iswalnum`、`regcomp` のマッチャー）に尋ねるので、ripgsed も同じライブラリに尋ねます。実行のロケールは `setlocale(LC_ALL, "")` が決めます。`LC_ALL`、`LC_CTYPE`/`LC_COLLATE`、`LANG` の優先順位、名前の綴り、`LOCPATH`、インストールされていない名前の失敗（すべてのカテゴリが `C` のままになる）はライブラリのもので、その規則の写しではありません。
- 有効にしておくのは `LC_CTYPE` と `LC_COLLATE` だけです。マッチャーが読むカテゴリはこの 2 つだけだからです。C ライブラリのメッセージ（`strerror`）と書式は、`C` ロケールのままです。
- `C` と glibc の `C.UTF-8` は、自前の表とバイト単位またはコードポイント順の規則を持ち、マッチ中にライブラリを呼びません。そのため、既定の経路の速度はライブラリに左右されません（D9）。それ以外の UTF-8 ロケールは、ライブラリの答えを使います。`\w` と単語アサーションには `iswalnum`、`\U \L \u \l` と `I` の下の後方参照には `towupper`/`towlower`、ブラケット式の中身（ロケールの照合順序による範囲、クラス、等価クラス、照合記号）と `I` の下の文字が何を表すかには、GNU sed も使う `regcomp`/`regexec` のマッチャーです。ロケールの照合順序は `wcscoll` だけでは得られません。glibc が範囲の端に使う順序は `wcscoll` の順序ではないからです（`en_US.UTF-8` で `[a-z]` は `A` を含みませんが、`wcscoll` は `A` を `a` と `b` の間に置きます）。ロケールのブラケット式は、すべてのコードポイントについて GNU sed と照合しています（`tools/locale-diff.py`）。
- 実物のプログラムで観察した、ライブラリのものではなく GNU sed 自身の規則が 2 つあります。GNU sed は、ライブラリのマッチャーの前に、すべてのパターンを最初のマッチャー（自前の DFA）に通します。このマッチャーは、単一の文字と ASCII 数字の範囲だけを持つブラケット式をコードポイントとして読み、マッチしない行にはまったくマッチしません。通った行の中のマッチの位置はライブラリが決めます。したがって `echo ٣ | sed 's/[0-9]/N/'` は `٣` を出力し、`echo 3٣ | sed 's/[0-9]/N/g'` は `NN` を出力します（`en_US.UTF-8` では、照合順序により `٣` は `[0-9]` に入ります）。ripgsed はそのようなパターンを 2 回コンパイルし、先にコードポイントとしての読みで尋ねます（`Regex::filter`）。2 つ目の規則：`I` の下では、リテラルの文字や単一の文字だけのブラケット式は、パターンがその異体字自体を書かない限り、小さなキリル文字の異体字 U+1C80..U+1C88 を取りません（`в` は `ᲀ` に一致しません）。
- 大文字小文字の規則と照合順序は、バグではなく仕様です（D10）。常にロケールのものです。ロケールによってだけ現れるマッチャーの癖は、docs/KNOWN-DIFFERENCES.md に挙げています。
- UTF-8 以外の文字集合も同じライブラリ呼び出しを使い、`Locale` の種類を 2 つ増やします。`Mb`（EUC-JP、Shift_JIS、GBK、Big5、EUC-KR、その他のマルチバイト集合）は、`mbrtowc` と `wcrtomb` で文字を読み書きします。glibc では `wchar_t` が文字集合によらず Unicode なので、`towupper`、`iswalnum`、`regcomp` は変えずに済み、括弧式はパターンのバイトのままコンパイルして、その集合自身の符号化で文字を尋ねます。`Sb`（ISO-8859-x、KOI8-R、Windows-125x、その他の単一バイト集合）は、バイトを文字のままにして、括弧式、`\w`、`I` の下の文字ごとに、256 バイトをライブラリに尋ねてバイト集合を埋めます。大文字小文字の変換はワイド文字を経由し（`btowc` の `towupper` を `wctob` で戻す。そのバイトがなければ 0xFF。GNU sed の出力がそうです）、ロケールは名前から推測せず `nl_langinfo(CODESET)` と `MB_CUR_MAX` で判定します。
- マルチバイト集合の事実のうち、速さを左右するものが 2 つあります。0〜127 のバイトが ASCII 文字かどうか（Shift_JIS は 0x5c と 0x7e を円記号とオーバーラインにします）と、マルチバイト文字のすべてのバイトが 0x80 以上かどうか（EUC-JP、EUC-KR は該当。2 バイト目が ASCII の Shift_JIS、GBK、Big5 は非該当）です。どちらも名前から決めず、起動時に `mbrtowc` で測ります。両方成り立つときは、ASCII バイトがそれだけで 1 文字であることを前提とする DFA とリテラル検索が、UTF-8 と同じ要領で ASCII のテキストの上で動きます（DFA は 0x80 以上のバイトで諦め、シミュレーションが引き継ぎます）。それ以外の集合では必要条件のリテラルだけを使って DFA は使わず、シミュレーションが文字単位で進み、マッチは文字境界から始め、位置の直前の文字は行を前向きに読んで探します（2 バイト目が 1 バイト目に見えることがあるので、後ろ向きには読めません）。
- GNU sed はマルチバイト集合ではスクリプトを文字単位で読みます（正規表現、`y` の文字列、その周りのテキストで、2 バイト目のバックスラッシュ、括弧、区切り文字は、その文字の一部です）が、`s` の置換文はバイト単位で読みます。どちらも再現します。追加のバイトを要求する先頭バイトはコマンドの区切りにできません（`delimiter character is not a single-byte character`）。集合の文字でないバイトはそのまま残り、`.` や括弧式にはマッチせず、`\U \L` はそこで止まります（不正な UTF-8 バイトと同じです）。
- 各集合のすべての文字と 2 バイト列を GNU sed 4.9 と比べました（`tools/locale-diff.py`。続けて `tools/locale-fuzz.py` でランダムなパターン）。残る差は docs/KNOWN-DIFFERENCES.md に挙げています。

## D12. grep モードは GNU grep 3.x に従う

- このプロジェクトは GNU grep としても振る舞います。同じコマンドラインに対して、同じ出力、メッセージ、終了状態を返します（grep についての D4 と D5）。モードは、プログラムが実行されるときの名前（`grep`、`egrep`、`fgrep`、`rgrep`）か、最初の引数 `--grep` で選びます。sed モードは変わりません。
- 基準は、期待結果を記録するマシンの GNU grep です（`tools/gen-fixtures.sh`）。sed モードの基準がそのマシンの GNU sed であるのと同じです（D6）。grep と PCRE2 の版は `tests/reference-grep.json` に記録します。CI は最新のランナーイメージ（`ubuntu-latest`）に追従し、その記録を比べます。ランナーが別の版を持ち込めば `fixtures` ジョブが失敗しますが、それは隠すものではなく、確かめるべき変化です。`tools/ref-grep.sh` は、別のリリースの grep と PCRE2 を取り出して、何が変わるかを見るためのものです。
- 正規表現エンジンは同じものです（D7）。GNU grep の構文（`Syntax::grep`）を読むよう頼まれ、GNU grep の DFA と C ライブラリのマッチャが食い違う場所では、両方の読み方（`Syntax::regex_semantic`）を持ちます。ロケールの規則は sed モードのものです（D11）。
- `-P` はシステムの PCRE2 ライブラリで、`dlopen` で開きます。そのため crate に依存はなく、ビルドの要件も増えません（D1、D8）。BSD ライセンスのライブラリを写すことはしません。GNU sed のソースを読まなかったのと同じく、GNU grep のソースも読んでいません。動かして挙動を調べ、それを実現するコードはここで書きました。
- GNU grep の挙動が明らかなバグである場合も、GNU sed の場合と同じ規則に従います（D10）。`-w -o` で、検索を始めた位置から測って短い一致を探す動作は、fixture とランダムテストが GNU grep の結果として示し、マニュアルがそれに反していないので、再現します。

## D13. ライブラリのインターフェースは小さい

- 公開するインターフェースは、`Script`（sed のテキスト、またはメソッドで組み立てたもの）、`Address` と `Pattern` を使う `Edit`（ビルダー）、`Run`（実行の設定。スレッドも含む）、`Outcome`、`Error` です。ほかのモジュールはすべて `#[doc(hidden)]` で、どのリリースでも変わりえます。
- ビルダーは sed のテキストを書き、コマンドラインのパーサーがそれを読みます。パーサーも VM も 1 つで、メソッドで作ったスクリプトは手で書いたスクリプトと同じものであり、間違いには GNU sed のメッセージが出ます。コマンドはアドレスと操作から成り、アドレスがないことは「すべての行を選ぶアドレス」です。
- ささいな仕事で素の Rust に勝つとは言いません。リテラル 1 つの置換なら `str::replace` のほうが速いです。このライブラリが与えるのは、GNU sed がスクリプトに込める意味（GNU sed 4.9 で確かめたもの）と、スクリプトが許すところでのスレッドです（測定した数字は `docs/GREP.md` と README にあります）。
