# 決定事項

これまでに決めたことと、その理由です。提案と未決の事項は [DESIGN.md](DESIGN.md) に置きます。決定は見直せますが、黙って消さずに、変更をここに記録します。

## D1. ライセンス：`MIT OR Apache-2.0`

- このプロジェクトは独立実装で、Rust のエコシステムで一般的なデュアルライセンスの `MIT OR Apache-2.0` でライセンスします。
- GPL のコードに由来するものは追加しません。GNU sed と GNU grep は参照としてだけ読み、コピーしません（DESIGN.md の由来の方針を参照）。

## D2. 入力表現：バイト列

- 入力、pattern space、hold space、出力は `String` ではなくバイト列です。GNU sed との完全互換には、不正な UTF-8 と NUL を受け付ける必要があります。
- レコード末尾の区切り（LF または NUL）は、レコード本文と別に保持します。最終改行がないことは保持し、正規化しません。
- P0 の対象は `C` ロケールのみで、`LC_ALL=C` の GNU sed と一致するバイト単位の挙動です。マルチバイトの文字単位の挙動（たとえば `.` が 1 文字にマッチする）は後の段階であり、それまでは達成したと主張しません。
- 入力はバッファ付きのストリームで読みます。メモリはファイル全体のサイズではなく、単一レコードの長さに応じて増えます。

## D3. 正規表現はエンジンの抽象化の裏に置く

- コアは正規表現ライブラリを直接呼びません。エンジンのインターフェース（DESIGN.md の「エンジンの抽象化」を参照）を使うので、このプロジェクト自身のエンジン（D7）と、opt-in の拡張としての PCRE2 などのエンジンを、並べて置けます。
- エンジンは（構文方言とオプションにより）明示的に選び、未対応の構文があっても黙って切り替えません。

## D4. GNU sed の完全互換は最低要件

- GNU sed と完全に互換になるまで、ripgsed は `sed` の代替としてリリースも説明もしません。完全互換とは、有効な GNU sed の呼び出しのどれに対しても、同じ stdout、終了状態、ファイルへの影響を返すことです。意図的に異なるのは、バージョン表記とヘルプの文面だけです（DESIGN.md を参照）。
- P0 のようなマイルストーンは作業の順序であり、小さな製品ではありません。この要件に関して、部分集合を「完了」と見なすことはありません。
- したがって範囲は、GNU sed のマニュアルにあるすべてです。すべてのコマンド、オプション、フラグ、エスケープ、アドレス形式、特殊なケースを含みます。互換性の一覧は最初からそれらをすべて挙げ、それぞれを未対応・部分対応・検証済みのいずれかとして記録し、未対応のものはコンパイル時エラーにします。
- 範囲には、マルチバイトと UTF-8 ロケールの挙動（D2 は作業の順序を決めただけで、まず `C` ロケール）と、`--debug` が明示的に含まれます。`--debug` の正規形のプログラム表示と実行の注釈も、ほかの出力と同様に GNU sed と比較します。
- 互換性は、GNU sed との差分テスト（リポジトリの tests/README.md を参照）でのみ検証し、主張だけで済ませることはありません。
- grep モードは、sed モードの後に、GNU grep について同じ水準を目指します。

## D5. 終了状態とエラーメッセージは GNU sed と完全に一致させる

- 終了状態は、文書化された 0・1・2・4 や `q`・`Q` に与えるコードを含め、すべての場合で GNU sed と同一です。
- stderr に出すエラーと警告のメッセージは、`C` ロケールの GNU sed のメッセージと一字一句同一です。`-e expression #1, char 3:` のような位置の部分も含みます。
- 呼ばれた名前に従うのはプログラム名の接頭辞だけです。`sed` として実行すれば `sed:`、`ripgsed` として実行すれば `ripgsed:` になります。これは名乗り方を意図的に変えたことの帰結であり、互換性の例外ではありません。
- gettext で他の言語に翻訳されたメッセージは、互換性の一覧のロケールの項目に属し、英語のメッセージの後に対応します。
- 差分テストは、stdout と終了状態に加えて stderr も比較します。

## D6. 互換の基準：GNU sed 4.9

- 挙動と、生成するテストの期待値の基準は、執筆時点で最新の安定版である GNU sed 4.9 です。
- 新しい GNU sed で変わった挙動は、黙って追従しません。互換性の一覧に別項目として記録し、基準のバージョンは改めて決めます。
- `--version` が出力するバージョン行には、この基準を明記します（DESIGN.md を参照）。

## D7. 正規表現エンジンは自前で書く

- つなぎとしても、サードパーティの正規表現ライブラリは使いません。POSIX の左端最長一致、後方参照、GNU 拡張を備えた GNU sed の BRE と ERE を、最初のリリースからこのプロジェクト自身のエンジンで実装します。
- 方言には、既定の GNU の挙動だけでなく、BRE と ERE の `--posix` と `POSIXLY_CORRECT` の変種、およびロケールが含まれます（D2 は作業の順序を決めたもので、まず `C` ロケール、その後に UTF-8 などのマルチバイトロケール）。
- 仕様は、GNU sed 4.9（D6）の観測できる挙動であり、POSIX と異なる箇所も含みます。その挙動は、GNU sed との差分テストが決めます。
- エンジンは D3 のインターフェースの裏にあるので、単独でテスト、ベンチマーク、ほかのエンジンとの比較ができます。

## D8. 対応プラットフォームとツールチェーン

- 最初に対応するプラットフォームは Linux です。差分テストは POSIX の `sh`、シンボリックリンク、参照としての GNU sed 4.9 に依存するため、Unix 系でのみ動きます。ほかのプラットフォームは、コアの検証が済んでから対応します。
- 対応する最小の Rust のバージョンは 1.85 で、edition 2024 を最初に備えたリリースです。`Cargo.toml` で宣言します。必要な機能があるときだけ引き上げ、その旨をここに記録します。
- サードパーティの依存は、`-P` 用の `pcre2-sys`（D14）の 1 つだけです。それ以外はありません（正規表現は D7 を参照）。依存を足すときは、その理由をここに記録します。

## D9. 速さは中核の目標：GNU sed 4.9 に勝つ（測定して）

- GNU sed 4.9 より速いことは、完全互換（D4）と並ぶこのプロジェクトの目標です。互換性が先で、どの最適化も出力を変えてはならないため、すべての変更は、差分 fixture とランダム差分テストを通し続ける必要があります。
- 「速い」は `tools/bench.sh` で定義します。決まった再現可能な workload（リテラルと正規表現の置換、アドレス照合、`y`、複数行サイクル、巨大な 1 行）を、同じマシンで GNU sed 4.9 と比べ、出力の一致をハッシュで確認します。主張にはマシン、ビルド、数値を添え、測っていない主張はしません。
- 作業は見込める効果の順に進めます。正規表現の探索（リテラルの先読み、後方参照のないパターンの DFA）、割り当てと I/O のオーバーヘッド、そして静的解析でレコード内で完結すると証明できたスクリプトの自動並列実行（DESIGN.md）です。それ以外は逐次にフォールバックします。
- 最初のリリースは、完全互換でベンチマークでも速くなるまで `sed` の代替とは呼びません。差が残るなら、数値の隣にその差を正直に書きます。

## D10. 完全互換。ただし C ライブラリの正規表現のバグは要求されたときだけ

- GNU sed 4.9 との互換性（D4）には3つの水準がある。(1) 文書化された、意図された挙動は、常に GNU sed と同じ。(2) 明らかなバグである挙動は、既定では修正された挙動、つまり定義どおりの結果にする。(3) バグそのものは、`--glibc-compat`（または `RIPGSED_GLIBC_COMPAT=1`）を付けたときだけ再現する。これは、まったく同じ出力を保つ必要がある既存の GNU sed 資産を移行するためのもの。
- 挙動がバグと見なされるのは、次のいずれかを満たす場合に限る。GNU sed のマニュアルか POSIX に反している。上流（glibc、GNU sed）が不具合と認めている。新しい版で修正されている。それ以外は挙動として扱い、水準 (1) に残す。
- 最初の例は、glibc の正規表現マッチャーの癖である。先頭の繰り返しの後ろにある `\B` の前の空マッチと、繰り返しの中のグループへの後方参照の不完全な探索（docs/KNOWN-DIFFERENCES.md）。`C.utf8` の文字クラス表はロケールの実装であって癖ではなく、常に有効にする。
- 差分テストと fixture は GNU sed と比較するので、オプションを付けて実行する。既定側は、定義どおりの結果を明記したテストで確かめる。互換性一覧（`compat/sed.tsv`）では、オプションを付けたときに GNU sed と一致する項目を verified とする。
- オプション名は、GNU sed の長いオプションの接頭辞を避けている（`--regex...` だと `--regexp-extended` の短縮形が曖昧になる）。

## D11. ロケールは C ライブラリのもの

- GNU sed はロケールのことを C ライブラリ（`setlocale`、`towupper`、`iswalnum`、`regcomp` のマッチャー）に尋ねるので、ripgsed も同じライブラリに尋ねます。実行のロケールは `setlocale(LC_ALL, "")` が決めます。`LC_ALL`、`LC_CTYPE`/`LC_COLLATE`、`LANG` の優先順位、名前の綴り、`LOCPATH`、インストールされていない名前の失敗（すべてのカテゴリが `C` のままになる）はライブラリのもので、その規則の写しではありません。
- 有効にしておくのは `LC_CTYPE` と `LC_COLLATE` だけです。マッチャーが読むカテゴリはこの 2 つだけだからです。C ライブラリのメッセージ（`strerror`）と書式は、`C` ロケールのままです。
- `C` と glibc の `C.UTF-8` は、自前の表とバイト単位またはコードポイント順の規則を持ち、マッチ中にライブラリを呼びません。そのため、既定の経路の速度はライブラリに左右されません（D9）。
  - それ以外の UTF-8 ロケールは、ライブラリの答えを使います。`\w` と単語アサーションには `iswalnum`、`\U \L \u \l` と `I` の下の後方参照には `towupper`/`towlower`、ブラケット式の中身（ロケールの照合順序による範囲、クラス、等価クラス、照合記号）と `I` の下の文字が何を表すかには、GNU sed も使う `regcomp`/`regexec` のマッチャーです。
  - ロケールの照合順序は `wcscoll` だけでは得られません。glibc が範囲の端に使う順序は `wcscoll` の順序ではないからです（`en_US.UTF-8` で `[a-z]` は `A` を含みませんが、`wcscoll` は `A` を `a` と `b` の間に置きます）。ロケールのブラケット式は、すべてのコードポイントについて GNU sed と照合しています（`tools/locale-diff.py`）。
- 2 つの規則は、ライブラリのものではなく GNU sed 自身のもので、実際のプログラムで観察したものです。
  - GNU sed は、ライブラリのマッチャーの前に、すべてのパターンを最初のマッチャー（自前の DFA）に通します。単独の文字と ASCII の数字どうしの範囲だけを持つブラケット式はコードポイントで読み、それがマッチしない行は、まったくマッチしないものとして扱います。
  - 通る行でマッチがある場合は、ライブラリが決めます。
  - そのため `echo ٣ | sed 's/[0-9]/N/'` は `٣` を出力し、`echo 3٣ | sed 's/[0-9]/N/g'` は `NN` を出力します（`٣` は、照合順序では `en_US.UTF-8` の `[0-9]` に含まれます）。ripgsed はそのようなパターンを 2 回コンパイルし、コードポイントの読み方を先に尋ねます（`Regex::filter`）。
  - 2 つ目の規則：`I` の下では、リテラルの文字や単独の文字のブラケット式は、パターンがその変種そのものを書かない限り、キリル文字の小文字の変種 U+1C80..U+1C88 を取りません（`в` は `ᲀ` にマッチしません）。
- 大文字小文字の規則と照合順序は、バグではなく仕様です（D10）。常にロケールのものです。ロケールによってだけ現れるマッチャーの癖は、docs/KNOWN-DIFFERENCES.md に挙げています。
- UTF-8 以外の文字集合は、`Locale` の 2 つの種類を足して、同じライブラリ呼び出しを使います。
  - `Mb`（EUC-JP、Shift_JIS、GBK、Big5、EUC-KR、そのほかのマルチバイト集合）は、`mbrtowc` と `wcrtomb` で文字を読み書きします。glibc の `wchar_t` はどの集合でも Unicode なので、`towupper`、`iswalnum`、`regcomp` は変える必要がなく、ブラケット式はパターンのバイトからコンパイルして、その集合自身の符号化で文字を尋ねます。
  - `Sb`（ISO-8859-x、KOI8-R、Windows-125x、そのほかの 1 バイト集合）は、バイトを文字として扱い、ブラケット式、`\w`、`I` の下の文字ごとに、256 バイトについてライブラリに尋ねてバイト集合を埋めます。大文字小文字の変換はワイド文字を経由します（`btowc` の `towupper`、次に `wctob`。そのようなバイトがなければ 0xFF で、GNU sed もそう出力します）。
  - ロケールは `nl_langinfo(CODESET)` と `MB_CUR_MAX` で調べ、名前から推測しません。
- マルチバイト集合の事実のうち、速さを左右するものが 3 つあります。0〜127 のバイトが ASCII 文字かどうか（Shift_JIS は 0x5c と 0x7e を円記号とオーバーラインにします）と、マルチバイト文字のすべてのバイトが 0x80 以上かどうか（EUC-JP、EUC-KR は該当。2 バイト目が ASCII の Shift_JIS、GBK、Big5 は非該当）です。
  - どちらも名前から決めず、起動時に `mbrtowc` で測ります。
  - 両方成り立つときは、ASCII バイトがそれだけで 1 文字であることを前提とする DFA とリテラル検索が、UTF-8 と同じ要領で ASCII のテキストの上で動きます（DFA は 0x80 以上のバイトで諦め、シミュレーションが引き継ぎます）。それ以外の集合では必要条件のリテラルだけを使って DFA は使わず、シミュレーションが文字単位で進み、マッチは文字境界から始め、位置の直前の文字は行を前向きに読んで探します（2 バイト目が 1 バイト目に見えることがあるので、後ろ向きには読めません）。
- GNU sed はマルチバイト集合ではスクリプトを文字単位で読みます（正規表現、`y` の文字列、その周りのテキストで、2 バイト目のバックスラッシュ、括弧、区切り文字は、その文字の一部です）が、`s` の置換文はバイト単位で読みます。
  - どちらも再現します。
  - 追加のバイトを要求する先頭バイトはコマンドの区切りにできません（`delimiter character is not a single-byte character`）。
  - 集合の文字でないバイトはそのまま残り、`.` や括弧式にはマッチせず、`\U \L` はそこで止まります（不正な UTF-8 バイトと同じです）。
- 各集合のすべての文字と 2 バイト列を GNU sed 4.9 と比べました（`tools/locale-diff.py`。続けて `tools/locale-fuzz.py` でランダムなパターン）。残る差は docs/KNOWN-DIFFERENCES.md に挙げています。

## D12. grep モードは GNU grep 3.x に従う

- このプロジェクトは GNU grep としても振る舞います。同じコマンドラインに対して、同じ出力、メッセージ、終了状態を返します（grep についての D4 と D5）。モードは、プログラムが実行されるときの名前（`grep`、`egrep`、`fgrep`、`rgrep`）か、最初の引数 `--grep` で選びます。sed モードは変わりません。
- 基準は GNU grep 3.11 と PCRE2 10.42 です。CI のランナーが持つリリースで、sed モードの基準が GNU sed 4.9 であるのと同じ位置づけです（D6）。
  - その版は `tests/reference-grep.json` に記録してあり、CI は最新のランナーイメージ（`ubuntu-latest`）に従って、その記録と比べます。ランナーが別のリリースを持ち込めば `fixtures` ジョブが失敗し、それは隠すのではなく見るべき変化です。
  - `tools/ref-grep.sh` が、あるリリースの grep と PCRE2 を取り出し（署名つきのアーカイブ索引で確かめます）、`GREP_DIR=... tools/gen-fixtures.sh` がそれで期待結果を記録するので、fixture はそのマシンの grep に依存しません。
  - 3.12 で違う点は、`src/grep/mod.rs` の `GNU_GREP_3_12` が選びます。ランナーが 3.12 になる日の手順は docs/GREP.md にあります。
- 正規表現エンジンは同じものです（D7）。GNU grep の構文（`Syntax::grep`）を読むよう頼まれ、GNU grep の DFA と C ライブラリのマッチャが食い違う場所では、両方の読み方（`Syntax::regex_semantic`）を持ちます。ロケールの規則は sed モードのものです（D11）。
- `-P` は PCRE2 ライブラリです。最初は `dlopen` で開いて、crate に依存もビルド要件も増やさないようにしました（D1、D8）。D14 でそれを crate `pcre2-sys` に置き換えました。GNU sed のソースを読まなかったのと同じく、GNU grep のソースも読んでいません。動かして挙動を調べ、それを実現するコードはここで書きました。
- GNU grep の挙動が明らかなバグである場合も、GNU sed の場合と同じ規則に従います（D10）。`-w -o` で、検索を始めた位置から測って短い一致を探す動作は、fixture とランダムテストが GNU grep の結果として示し、マニュアルがそれに反していないので、再現します。

## D13. ライブラリのインターフェースは小さい

- 公開するインターフェースは、`Script`（sed のテキスト、またはメソッドで組み立てたもの）、`Address` と `Pattern` を使う `Edit`（ビルダー）、`Run`（実行の設定。スレッドも含む）、`Outcome`、`Error` です。ほかのモジュールはすべて `#[doc(hidden)]` で、どのリリースでも変わりえます。
- ビルダーは sed のテキストを書き、コマンドラインのパーサーがそれを読みます。パーサーも VM も 1 つで、メソッドで作ったスクリプトは手で書いたスクリプトと同じものであり、間違いには GNU sed のメッセージが出ます。コマンドはアドレスと操作から成り、アドレスがないことは「すべての行を選ぶアドレス」です。
- ささいな仕事で素の Rust に勝つとは言いません。リテラル 1 つの置換なら `str::replace` のほうが速いです。このライブラリが与えるのは、GNU sed がスクリプトに込める意味（GNU sed 4.9 で確かめたもの）と、スクリプトが許すところでのスレッドです（測定した数字は `docs/GREP.md` と README にあります）。

## D14. `-P`: sed モードの PCRE2 パターン

- 依存先は `pcre2-sys`（`Unlicense OR MIT`、ripgrep の作者によるもので、ダウンロード数は 400 万超）です。PCRE2（BSD-3-Clause WITH PCRE2-exception）のソースを抱えたバインディングで、C コンパイラでビルドします。
  - ビルドに C コンパイラが要り、crate に依存が 1 つ（ビルド時には `cc`、`pkg-config`、`libc` も）増えるという代償があります。それでも、自前の純 Rust エンジン（数週間の仕事で、差を追い続ける必要がある）や、システムのライブラリを `dlopen` で開く方法（最初の版。依存はないが、ライブラリのない環境で `-P` が失敗し、ライブラリの版もマシン次第）より、これを選びました。
  - この grep や sed を使う人は `rg` や `fd` も使い、`cargo` でビルドする人たちで、`cargo` の環境には C コンパイラがもともとあります。
  - 将来、同じ `src/pcre.rs` の裏側を純 Rust のエンジンに置き換えることもできます。
  - 高水準の crate `pcre2` ではなく低水準のバインディングを使うのは、`-P` が `DOLLAR_ENDONLY` と `MATCH_INVALID_UTF` を必要とし、パターンがバイト列だからです。
- `-P` / `--perl-regexp` は grep の同名オプションの綴りで、GNU sed では `-P` が使われていないため、GNU sed で動くスクリプトには影響しません。後ろに `-E` を付けると元に戻ります。
- grep の `-P` と同じライブラリ（`src/pcre.rs`。D12）を、crate `pcre2-sys` 経由で使います。
  - `Regex::compile_pcre` が作る `Regex` はコンパイル済みのパターンを持ち、`is_match`、`captures_at`、`group_count` にそれで答えます。コマンド、置換部、空の正規表現（直前のものを再利用）、フラグ `I` と `M` は sed のままです。
  - `I` は大文字小文字を区別せず、`M` は複数行モードで、`M` がなければ `$` はパターンスペースの末尾にだけ一致します（`DOLLAR_ENDONLY`）。
  - UTF-8 ロケールではパターンもテキストも UTF-8 として扱い（不正なテキストはエラーにしません）、`\w`、`\b`、文字クラスは Unicode を知っています。
- パターンは PCRE2 のものなので、`(?s)` がなければ `.` は改行に一致せず、`\d` は数字（sed の `\dNNN` ではない）で、`\n`、`\t`、`\xHH` はライブラリの意味です。ブラケット式の中の区切り文字は Perl と同じくエスケープが必要で、`[/]` を sed の読み方で扱うことはしません。`M` はライブラリのビルド時の改行（LF）を使い、`-z` のときも同じです。
- ライブラリにも同じものがあります。`Pattern::perl` と `Script::parse_perl`、そして拡張パターンの旗の代わりに `Script::dialect`（`Dialect::{Basic, Extended, Perl}`）です。スクリプトの方言は 1 つで、混ぜると組み立て時にエラーになります。
- 比較できる GNU sed がないため、テストはライブラリの答えを期待値にしています（`tests/cli.rs`）。`--debug` はパターンを書いたとおりに表示します。

## D15. 最後から数えるアドレス：`$-N` と `addr,-N`

- GNU sed 4.9 はどちらもエラーにするので、GNU sed で動くスクリプトには影響しない（`-P`、D14 と同じ）。切り替えのスイッチはなく、その書き方をしたことが指定になる。代償は、これらを使ったスクリプトが GNU sed では止まること。
- `$-N` は、後ろに N 行ある行。`$-0` は `$`。アドレスとして、また範囲の終わり（`addr,$-N`）として書ける。`-s` と `-i` では、そのファイルの中で数える。
- `addr,-N` は、`addr` とその前の N 行。`addr,+N` が `addr` とその後ろの N 行であるのと対になる。`10,-3` は `7,10`、`-0` は `+0` と同じく 1 行。`addr` は行番号、`$`、`$-N` のどれかでなければならない。正規表現やステップのあとでは、その前の行はもう過ぎているので、エラーになる。
- マイナスの行番号そのもの（`-3,$`）は受け付けない。スクリプトを読む前に、コマンドラインがそれをオプションとして読んでしまうため。
- `$,-9!d` は、`tail -10` と同じく最後の 10 行を残す。入力を N レコード先まで先読みして実現する。チャンクの実行器には、チャンクの後ろに何レコード続くかを（スクリプトが見たい数まで）伝えるので、これらのスクリプトも並列で動く。
- 比べる GNU sed がないので、答えは fixture ではなく、行のモデルから `tests/from_end.rs` に書いてある。fixture `adr-019-invalid-address-forms` から `2,-1p` を外した（GNU sed は拒否し、ripgsed は受け付けるため）。

## D16. 近道は解析が証明する計画であり、逐次の VM がそれと一致すべき基準である

- スクリプトは、それを構成するコマンド（構文木）として読まれ、その解析（`src/analysis.rs`）によって、入力のある部分は読まなくてよい、あるいは別の方法で読めると分かることがある。分かったことは計画であり、サイクルをすべてのレコードで実行する逐次の VM が、計画の答えが一致すべき基準であり続ける。
- いまある計画：
  - スレッド：レコード間で何もしないスクリプト（`record_local`）は、チャンクごとに実行する。範囲の状態は推測して、外れたらやり直し、出力は順に戻す。
  - ファイルの末尾（`tail_window`）：`-n '$p'`、`$!d`、`-n '$-9,$p'`。最後の数レコードより前は何も残さないので、最後の数レコードをファイルの末尾から読む。
  - 先頭（`head_limit`）：`-n '1,10p'`、`3!d`。最後の行番号より後は何も残さないので、そこで実行を止める。
  - 両端（`head_tail_plan`）：`-n '1p;$p'`。
  - ステップの次の行（`skip_ahead`）：`-n '0~1000p'`。
- 計画は、どのアドレスも真にならない（正規表現以外のアドレスはすべて偽）レコードについて証明する。そのレコードに対して動きうるコマンドを最初から順にたどり、レコードが削除されるか、スクリプトが終わって静か（`-n`）になるまで、どのコマンドも何も残さない（出力、書き込み、保持、先読みをしない）ことを示す。示せないものは計画ではなく、VM で実行する。
- 実行の開始時に確かめるのは入力である。コマンドラインで名前を指定したファイル、または通常ファイルである標準入力（pipe は対象外。pipe に書き込む側のプロセスに見えるし、早く止める実行はそれを変えてしまう）。早く止める計画では、名前を指定したすべてのファイルが読めることも確かめる（通常の実行が報告するはずのことを見逃さないため）。満たさなければ、まだ何も書いていないので、通常の実行が続き、答えは同じになる。
- 計画にはスイッチがある（`RIPGSED_JOBS`、`RIPGSED_TAIL=0`、`RIPGSED_TAIL_MIN_BYTES`、`RIPGSED_HEAD=0`）。計画と VM を比べるテストは、どんなに小さいファイルでも、計画をすべてのファイルで強制して実行する。末尾を読む強制（`RIPGSED_TAIL_MIN_BYTES=0`）でのフィクスチャ（GNU sed の結果）とランダムなスクリプト、および 4 スレッド・16 バイトのチャンクでのフィクスチャ。CI では `forced` の job が行う。間違った計画は、何も言わずに間違った答えを出すので、遅いよりも悪い。テストが強制しないものには、頼らない。
- 計画が使われることを確かめるテストは、空洞（疎ファイル）の数 GiB のファイルを、その計画を使わない実行が持たないメモリ（`ulimit -v`）の下で読む。そのようなテストのプログラムは、すべて、書き出せる量に上限を付ける（AGENTS.md）。
