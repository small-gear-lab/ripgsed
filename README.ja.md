# ripgsed

[English](README.md)

Rust で書いた、高速な GNU sed 4.9。コマンドとしても、ライブラリとしても使えます。同じプログラムが grep にもなります。

> **状態: 実験的（0.1）。** 目標は、GNU sed（と grep）をそのまま置き換えられることです。以下に書くことは、テストで確かめられている範囲のものです。ライブラリのインターフェースは 1.0 までに変わるかもしれません。また、動作確認は Linux だけです。

名前は、見たままの意味です。速い gsed（GNU sed）です。

## できること

- **GNU sed 4.9 と同じように動く sed。** sed 言語、自前の正規表現エンジン（BRE、ERE、`--posix`）、`-i`、`-z`、`-s`、`--debug`、`w`/`r`/`R`/`W`、そして C ロケールと C ライブラリのすべてのロケール（UTF-8、EUC-JP、Shift_JIS、GBK、GB18030、Big5、EUC-KR、EUC-TW、ISO-8859-x、KOI8-R、Windows-125x）。
- **GNU sed より速い。** 1 行ずつ独立して処理できると確かめられたスクリプトは複数のスレッドで動くので、大きなファイルではとくに速くなります（「速度」を参照）。
- **grep。** `grep`、`egrep`、`fgrep` の名前で（または `--grep` で）起動すると、GNU grep 3.x として動きます。`-P` も、ディレクトリツリーの複数スレッド検索も使えます。
- **sed での Perl 風のパターン。** `ripgsed -P 's/(\d+)(?=px)/<$1>/g'`（PCRE2）。
- **最後から数えるアドレス**：`ripgsed '$,-9!d'` は `tail -n10` と同じく最後の 10 行を残し、`$-2,$p` は最後の 3 行を出力する。GNU sed はこれらの書き方を拒否する（D15）。
- **スクリプトが必要とするところだけを読む**：入力がファイルのとき、`sed -n '$p' file` はファイルの末尾を読み、`sed -n '1,10p'` は 10 行で止まり、`sed -n '1p;$p'` は両端を読み、`sed -n '0~1000p'` は 1000 行目ごとの間の行を数えるだけで済ませる（D16）。どの場合も、GNU sed は入力をすべて読む。
- **Rust のライブラリ。** 同じ sed 言語を使え、スクリプトを組み立てるビルダーもあります。

## 互換性の確かめ方

- 互換性マトリクスに 261 の挙動を挙げています（GNU sed のマニュアルと、テストが見つけた違いから）。そのすべてを、本物の GNU sed 4.9 と比べる 1,889 個の差分 fixture で確かめています：[docs/ja/COMPATIBILITY.md](docs/ja/COMPATIBILITY.md)。
- 正規表現と、スクリプト全体のランダムな差分テストは、約 99.9% のケースで GNU sed と一致します。
- fixture は GNU sed 自身のコードの 95.7% の行を実行し、ripgsed 自身のテストは、自分のコードの 99% の行を実行します。
- 互換性は、fixture が確かめた範囲だけを主張します。

既知の違いは [docs/ja/KNOWN-DIFFERENCES.md](docs/ja/KNOWN-DIFFERENCES.md) にあります。それらは C ライブラリの正規表現マッチャーのバグで、既定では、ripgsed は定義どおりの結果を返します。`--glibc-compat`（または `RIPGSED_GLIBC_COMPAT=1`）は、そのとおりの結果が必要なまれなスクリプトのために、GNU sed の結果をそのまま再現します（D10）。

## インストール

```sh
cargo install ripgsed          # Rust 1.85 以降と C コンパイラが必要（PCRE2 のため。-P を参照）
ln -s "$(command -v ripgsed)" ~/.local/bin/sed    # sed として ...
ln -s "$(command -v ripgsed)" ~/.local/bin/grep   # ... grep として（egrep、fgrep も）
```

プログラムは、起動された名前で動作モードを決めるので、リンクを作るだけで済みます。リンクなしで grep を使うには `ripgsed --grep ...` です。どの sed でも同じように動かさなければならないスクリプトでは、`ripgsed` を名前で呼んでください。

開発とテストは Linux（Ubuntu、glibc）で行っていて、GNU sed 4.9 との互換性は、そこで確かめています。macOS（Apple Silicon、CI）では、ビルドでき、プログラム自身のテストが通り、そこに当てはまる 1,879 個の fixture が通ります（glibc のロケール、`/dev/full`、`/proc`、Linux での `/dev/stdin` の開き方に関するものは除いています）。ロケールは名前から判定する `C` か UTF-8 で、ほかのマルチバイトの文字集合はバイト列として読みます。macOS の標準の sed は BSD sed で、GNU sed は `gsed`（`brew install gnu-sed`）として入ります。ripgsed は速い `gsed` なので、その名前でリンクしてください（`ln -s ~/.cargo/bin/ripgsed ~/.local/bin/gsed`）。エディタとの連携は実装していません。

## 速度

`tools/bench.sh` が、決まったワークロード（100 万行のログ風の行。出力の一致はハッシュで確認）で、ripgsed と GNU sed 4.9 を比べます。

- 時間は 5 回の中央値で、単位は秒です（`-s -n '$p'` の行は、測り直したので 51 回の中央値です）。Intel Core i7-1260P（16 スレッド）、Linux、リリースビルドで測りました。
- ロケールは `LC_ALL=C.UTF-8` です。UTF-8 ロケールで、難しいほうの場合です。`BENCH_LOCALE=ja_JP.UTF-8 tools/bench.sh` は C ライブラリを通るロケールを測ります。そこでは `\w` を使う日本語のワークロードの時間がおよそ 2 倍になりますが、それでも GNU sed より速いです。
- 「auto」は既定のモードです。静的解析で、レコード単位で完結すると確かめられたスクリプトは、大きな通常ファイルで並列に動きます。`-s` と `-i` でも並列に動きます（各ファイルはそれぞれ別のストリームで、ファイルは複数のスレッドで編集されます）。

- **逐次実行**: 他のレコードを読む（`n`、`N`、`D`）、ホールドスペースを使う、ファイルを読む・コマンドを実行する（`r`、`R`、`e`）スクリプトは逐次実行になります。1 スレッドでの逐次実行の経路は、上のどの処理でも GNU sed より速いです（2 ファイルの `-s -n '$p'` は、`$` のために先読みしたレコードをキューに通していたときは 51 回の測定で 1.33 倍でしたが、今は 0.83 倍です）。比が 0.00 というのは、時間が 0.005 秒より短いということで、ファイルの先頭か末尾だけを読むスクリプトです。どの処理でも、出力が GNU sed と一致することを確認しています。

## grep として

`ln -s ripgsed grep`（`egrep`、`fgrep` も）、または `ripgsed --grep ...`：オプション、出力、メッセージ、終了状態は GNU grep と同じです。C ロケールでも、C ライブラリのロケールでも同じです。

- **確かめ方**：[compat/grep.tsv](compat/grep.tsv) の 83 項目を、GNU grep 3.11 と PCRE2 10.42（CI のランナーが持つもの）で作った 89 個の fixture で確かめています。3.12 で変わる 4 点は、ソースの 1 つのスイッチです（[docs/ja/GREP.md](docs/ja/GREP.md) を参照）。ランダムなパターンとランダムなオプションの組み合わせは、約 500 件に 1 件を除いて GNU grep と一致します。
- **入力**は、読みながら検索します。パイプは届いたそばから、メモリより大きなファイルでも大丈夫です。
- **ディレクトリツリー**は複数のスレッドで検索し、出力は 1 スレッドで検索したときの順序になります。1,000 ファイル（71 MB）のツリーで、`-rc ERROR` は GNU grep の 0.103 秒に対して 0.023 秒です。
- **1 スレッド、57 MB のログ行**で、ripgsed を、このマシンの GNU grep（3.12）と時間の比で比べると（1 より大きいと遅い）、リテラルは 1.0〜1.2（`-c` と `-F` は同じ。`-i` は速く、まれなリテラルは 0.7）、`-o` は 0.7、`-w` は 0.4、日本語テキストの `\w` は 0.2 です。遅いのは、繰り返しを含む選択肢で約 1.9、後方参照で 2.4 です。表と違いは [docs/ja/GREP.md](docs/ja/GREP.md) にあります。
- **`-P`** は PCRE2 で、プログラムと一緒にビルドします。

## Perl 風のパターン：`-P`

`ripgsed -P 's/(\d+)(?=px)/<$1>/g'`、または `--perl-regexp`（grep の `-P` と同じ綴りです。GNU sed にはこのオプションがありません）。

- スクリプトの正規表現（アドレスと `s` の中）は PCRE2 のものになります。ライブラリは crate `pcre2-sys` を通してプログラムと一緒にビルドするので、ビルドには C コンパイラが要ります。
- コマンド、フラグ `I` と `M`、置換部（`\1`、`&`、`\U`）、空の正規表現は sed のままです。パターンの意味だけが PCRE2 のものです。
- `--posix` は GNU の拡張を無効にするオプションで、`-P` は GNU sed にはそもそもない拡張である。`--posix` と `-P` を一緒に指定すると使い方のエラーになる（`-P -E` は最後に指定したほうが有効になり、ERE として扱われる）。
- ライブラリにも同じ機能があります（`Pattern::perl`、`Script::parse_perl`）。
- 比べられる GNU sed がないので、結果はライブラリのものです。`tests/cli.rs` でテストしています（D14）。

## ライブラリとして

スクリプトは、コマンドの並びです。各コマンドは、アドレスと操作でできています（アドレスがなければ、すべての行が対象です）。sed のテキストとして書くことも、メソッドで組み立てることもでき、どちらも同じ `Script` になります。`Run` が、それをリーダー、ライター、バイト列に適用します。

```rust
use ripgsed::{Address, Edit, Pattern, Run, Script};

// sed のテキストとして ...
let script = Script::parse("2,3d;s/foo/bar/g")?;
// ... またはメソッドで。ビルダーは sed のテキストを書き、同じパーサーがそれを読むので、
// 誤り（`q` に範囲を付けた、未知のラベル）には GNU sed のメッセージが出ます。
let same = Edit::new()
    .when(Address::lines(2..=3)).delete()
    .substitute(Pattern::basic("foo"), "bar").global()
    .build()?;

let out = Run::new().jobs(0).apply(&same, b"foo\nfoo\nfoo\nfoo foo\n")?;
assert_eq!(out, b"bar\nbar bar\n");
```

まだメソッドのないコマンド（ホールドスペース、`n` `N` `D` `P`、`r` `w`、ラベル）は、`Edit::raw("1!G;h;$!d")` で入れます。`Run::jobs` は、行が互いに独立しているスクリプトをスレッドに分け、出力はバイト単位で同じです。`Run::glibc_compat` は C ライブラリのマッチャーの癖を再現します。

単純な仕事では、素の Rust には勝てません。55.6 MB のログ風の行で測ると、次のとおりです。

- リテラルの `str::replace` は、同じ `s/alpha/X/g` を 1 スレッドで ripgsed に通すより、約 2.7 倍速いです。
- `regex::Regex::replace_all` は、`s/[0-9]+/N/g` より約 1.7〜2.3 倍速いです。
- 小さな入力（100 行）を、組み立て済みのスクリプトに通すと、組み立て済みの `regex::Regex` で同じことをするより、約 2 倍の時間がかかります。

ライブラリが与えるのは、GNU sed がスクリプトという言葉で意味するもの（アドレスと範囲、`s` のフラグ、大文字小文字の変換、ロケールの規則）で、GNU sed 4.9 と照らして確かめてあり、スクリプトが許すときにはスレッドも使います。リテラル 1 つの置換なら、`str::replace` を使ってください。

## 方法と、この先

GNU sed 4.9 との完全な互換性を、差分テストで確かめます（[docs/ja/DECISIONS.md](docs/ja/DECISIONS.md) の D4）。grep モード（D12）、`-P`（D14）、ライブラリのインターフェース（D13）も、同じ方法に従います。自動並列化と DFA による正規表現の検索は sed モードにあり、grep モードではツリーのファイルを並列に検索します。この先は、エディタとの連携、grep の遅いケースの高速化、そして、C のビルドが重荷になるなら、`src/pcre.rs` の裏にある純 Rust の PCRE2 エンジンです。

- [docs/ja/DESIGN.md](docs/ja/DESIGN.md)：目標、意味、未決の事項
- [docs/ja/ARCHITECTURE.md](docs/ja/ARCHITECTURE.md)：現在のモジュール構成と方針
- [tests/README.md](tests/README.md)：fixture の作り方

## ドキュメント

ドキュメントは英語で書き、Sphinx で英語と日本語のものをビルドします。HTML は CI がビルドして GitHub Pages に公開するので、リポジトリには入れていません。日本語訳は `docs/locale/ja/LC_MESSAGES/*.po` にあり、そこから作った日本語の Markdown は [`docs/ja/`](docs/ja/index.md) に入れてあるので、GitHub でそのまま読めます。`README.ja.md` も同じ方法で、`docs/locale/ja/LC_MESSAGES/readme.po`（コードブロックは `docs/locale/ja/readme-code.json`）から作ります。

```sh
tools/build-docs.sh          # 英語と日本語の HTML をビルドして docs/ja を作り直す
tools/build-docs.sh update   # 先に、英語のソースから .po ファイルを更新する
```
